# پروتکل تداوم کار در چت‌های آینده

این پروتکل برای آن است که دانش پروژه به یک حساب، یک چت یا حافظهٔ موقت وابسته نباشد.

## آغاز هر جلسه

ابتدا باید این فایل و `PROJECT-CONTINUITY.md` خوانده شوند. سپس وضعیت زیر بررسی شود:

```bash
git status --short
git log --oneline --decorate -15
pnpm check
```

برای کار دامنه‌ای، `PROJECT-REFERENCE.md` و سند مربوط به همان بخش نیز باید خوانده شود. برای کار روی داده، آخرین بکاپ باید فقط پس از اعتبارسنجی ساختار و نسخهٔ آن استفاده شود.

## طبقه‌بندی درخواست‌ها

هر درخواست در یکی از این طبقه‌ها ثبت شود:

- **تحلیل:** بدون تغییر کد؛ نتیجه و ابهام‌ها در `DECISION-LOG.md` ثبت می‌شود.
- **اصلاح:** تغییر کد یا مستندات؛ فایل‌های تغییرکرده، دلیل و آزمون ثبت می‌شود.
- **قابلیت جدید:** ابتدا قرارداد داده و UX مشخص می‌شود، سپس پیاده‌سازی انجام می‌شود.
- **بازیابی:** ابتدا منبع سالم انتخاب و checksum/نسخه کنترل می‌شود؛ هرگز بکاپ مشکوک مستقیماً روی دادهٔ اصلی restore نمی‌شود.
- **انتشار:** check، build، تست سناریو، کنترل backup و گزارش release الزامی است.

## قواعد ثبت تصمیم

هر تصمیمی که رفتار مالی، مدل داده، واحد، تاریخ، وضعیت چک، دسترسی، backup یا UX را تغییر دهد، باید در `DECISION-LOG.md` ثبت شود. قالب هر ورودی:

```markdown
## YYYY-MM-DD — عنوان تصمیم

**درخواست:** چه مسئله‌ای مطرح شد؟

**بررسی:** چه فایل‌ها، داده‌ها یا سناریوهایی بررسی شد؟

**تصمیم:** رفتار نهایی چیست؟

**دلیل:** چرا این گزینه انتخاب شد؟

**اثر:** چه بخش‌هایی تحت تأثیر قرار می‌گیرند؟

**آزمون:** چه تستی اجرا شد و نتیجه چه بود؟

**وضعیت:** باز / انجام‌شده / نیازمند بازبینی
```

## قواعد تغییر کد

تغییرات باید کوچک، قابل بازگشت و قابل ردیابی باشند. قبل از تغییر قرارداد داده باید migration و اثر آن بر بکاپ‌های قدیمی مشخص شود. هیچ فیلد مالی بدون تعیین واحد، مبنای مبلغ، تاریخ مؤثر و روش نمایش اضافه نشود.

هر تغییر باید حداقل یک آزمون متناسب داشته باشد. تغییر در فاکتور، چک، FIFO، واحد، تولید یا گزارش بدون سناریوی مرزی پذیرفته نیست. دادهٔ واقعی کاربر نباید برای تست داخل Git یا فایل عمومی commit شود.

## قواعد پایان جلسه

پیش از پایان:

1. تست‌های مرتبط اجرا شوند.
2. `git diff` و `git status` بررسی شوند.
3. تصمیم‌ها و خطاهای جدید در `DECISION-LOG.md` نوشته شوند.
4. `PROJECT-CONTINUITY.md` فقط در صورت تغییر وضعیت کلی به‌روزرسانی شود.
5. commit با پیام توصیفی ساخته شود، مگر آن‌که کاربر صریحاً commit نخواهد.
6. اگر کاری نیمه‌تمام است، فایل، خط، علت توقف و گام بعدی نوشته شود.

## سیاست بکاپ

برای هر تغییر معنی‌دار حداقل این سه مورد نگهداری شود:

- commit کد در Git؛
- خروجی JSON قبل از migration یا تغییر مدل؛
- یادداشت نسخه، تاریخ، checksum و نتیجهٔ restore آزمایشی.

Drive برای نگهداری نسخه‌ها مناسب است، اما نباید تنها نسخه باشد. Client Secret، توکن، رمز عبور و دادهٔ احراز هویت هرگز در دفتر پروژه ثبت نمی‌شود.

## پروتکل هنگام تعلیق حساب یا از دست‌رفتن چت

ابتدا از تلاش برای حدس‌زدن محتوای چت خودداری شود. مرجع بازیابی به‌ترتیب زیر است:

1. ریپوزیتوری اصلی و commit آخر؛
2. `docs/` و `CHANGELOG.md`؛
3. آخرین بکاپ JSON معتبر محلی؛
4. نسخه‌های Google Drive؛
5. Google Sheets و ریپوزیتوری تاریخی فقط برای تطبیق و کشف سابقه.

بعد از بازیابی، checksum و ساختار بکاپ بررسی شود. سپس یک محیط جدا برای restore آزمایشی ساخته شود. فقط بعد از موفقیت تست، داده در محیط کاری وارد شود.

## چه چیزی نباید ثبت شود

این پروتکل برای ثبت دانش فنی است، نه محل ذخیرهٔ اسرار. موارد زیر ممنوع‌اند:

- رمز عبور و کد بازیابی؛
- OAuth token، refresh token و Client Secret؛
- لینک عمومی حاوی دادهٔ خصوصی؛
- شماره‌ها یا اطلاعات شخصی غیرضروری مشتریان؛
- بکاپ کامل دادهٔ واقعی داخل مخزن عمومی.

## معیار انتقال به نفر یا عامل جدید

عامل جدید زمانی آمادهٔ ادامه است که بتواند بدون دسترسی به چت‌های قبلی توضیح دهد: معماری فعلی چیست، آخرین commit کدام است، داده کجا نگهداری می‌شود، ریسک‌های باز چیست، آخرین تست‌ها چه نتیجه‌ای داشته‌اند و گام بعدی چرا انتخاب شده است.
