## هدف این دفتر

این فایل نقطهٔ شروع هر ادامهٔ کاری در چت‌های آینده است. هدف آن حفظ دانش پروژه در خارج از حافظهٔ یک حساب کاربری یا یک گفت‌وگوی خاص است. هر جلسهٔ مهم باید وضعیت، تصمیم‌ها، خطاها، تغییرات و گام بعدی را در همین ساختار یا فایل‌های پیوست آن ثبت کند.

> اصل تداوم: هیچ تصمیم مهم، راه‌حل، خطای شناخته‌شده یا تغییر رفتاری نباید فقط در چت باقی بماند.

## وضعیت فعلی پروژه

پروژه یک برنامهٔ حسابداری کارگاه به‌صورت local-first و PWA است. داده‌ها در مرورگر نگهداری می‌شوند و قابلیت خروجی/بازیابی JSON و اتصال اختیاری به Google Drive دارد. حوزه‌های فعلی شامل طرف حساب، کالا و واحد، انبار، فاکتور خرید و فروش، عملیات مالی، بانک و صندوق، چک، تخصیص FIFO، تولید، گزارش‌ها، تنظیمات و پشتیبان‌گیری است.

ریپوزیتوری اصلی منبع حقیقت کد است. ریپوزیتوری `rasool083/Accounting-` منبع تاریخی و مستندات اولیهٔ مدل‌های Excel/Sheet و گفت‌وگوهای آغازین محسوب می‌شود. فایل‌های Google Drive و Google Sheets منبع داده‌ها، مثال‌ها و نسخه‌های پشتیبان هستند؛ آن‌ها بدون بررسی تاریخ و نسخه نباید منبع حقیقت کد تلقی شوند.

## ریسک‌های باز و حل‌نشده

این موارد باید در هر برنامه‌ریزی آینده در نظر گرفته شوند:

1. قرارداد قیمت و واحد باید در مدل با `priceBasis` و نمایش صریح واحد قیمت تثبیت شود.
2. هستهٔ تقویم جلالی و اختلاف روز یکسان‌سازی شده است؛ نمایش صریح `dayBasis` و آزمون UI با دادهٔ واقعی هنوز باقی است.
3. موجودی کالا و ماندهٔ حساب‌ها projection مستقیم هستند، نه حاصل دفتر رویداد بازسازی‌پذیر.
4. حذف انبار و کالاهای دارای ارجاع باید به آرشیو یا خطای وابستگی تبدیل شود.
5. کاردکس باید بالانس، مصرف واقعی تولید، nested production و snapshot را کامل نمایش دهد.
6. تست integration/UI با fixture عملیاتی غیرحساس هنوز کافی نیست.
7. پرتال مشتری بدون authentication، tenant و Row-Level Security قابل انتشار نیست.
8. برای APK باید migration، PWA cache، quota، backup/restore و update موبایل جداگانه آزموده شوند.

### برنامهٔ باقی‌مانده

چهار مرحلهٔ توسعه‌ای اصلی باقی است: (۱) اتصال کامل reversal به تمام مسیرهای ویرایش و حذف فاکتور و پرداخت، (۲) کنترل حساب‌ها و مغایرت بانکی و انتقال بین حساب‌ها، (۳) سخت‌سازی PWA و آماده‌سازی APK، و (۴) طراحی پورتال امن و read-only مشتری. پس از این چهار مرحله، یک مرحلهٔ نهایی آزمون پذیرش و انتشار پایدار با سناریوهای واقعی تولید، خرید، فروش، چک، تأمین‌کننده و شریک انجام می‌شود.

بنابراین **۴ مرحلهٔ توسعه‌ای و ۱ مرحلهٔ انتشار نهایی** باقی مانده است.


## ۱۴۰۵/۰۶/۳۱ — تکمیل مرحلهٔ reversal فاکتور خرید

مرحلهٔ آزادسازی پرداخت در ویرایش، ابطال و حذف فاکتور خرید با commit بعدی این جلسه تکمیل می‌شود. پرداخت‌های اختصاصی آزاد می‌شوند، اما پرداخت‌های FIFO مشترک میان چند فاکتور حفظ می‌گردند. چک مشتری، چک شریک و رویداد نقدی/بانکی هرکدام مسیر reversal مستقل دارند و از ایجاد reversal تکراری جلوگیری می‌شود.

آزمون‌های مرحله ۲۹ مورد موفق بودند و type-check و build نیز موفق شدند. هشدار build دربارهٔ بزرگ‌بودن chunk جاوااسکریپت مانع انتشار نیست و به مرحلهٔ بهینه‌سازی عملکرد منتقل می‌شود.

**گام بعدی:** مرحلهٔ کنترل حساب‌ها و مغایرت بانکی شامل projection-first، انتقال بین حساب‌ها، گزارش مغایرت و کنترل رویدادهای سررسیدشده.


## ۱۴۰۵/۰۶/۳۱ — تکمیل مرحلهٔ کنترل حساب‌ها و مغایرت بانکی

گزارش تطبیق حساب‌ها اکنون برای بانک، صندوق و شریک، ماندهٔ ثبت‌شده را با ماندهٔ بازسازی‌شده از دفتر نقدی مقایسه می‌کند و اختلاف، دریافت، پرداخت و تعداد رویدادها را نمایش می‌دهد. انتقال بین حساب‌ها و ماندهٔ افتتاحیه با آزمون مستقل پوشش داده شدند.

در ممیزی اجرایی، خطای preview ناشی از دو مسیر React کشف شد. تنظیمات Vite مخزن و محیط preview با alias و `dedupe` برای React و ReactDOM اصلاح شدند. بعد از اصلاح، dashboard، صفحهٔ بانک‌ها و صندوق‌ها و گزارش‌ها در مرورگر قابل اجرا و قابل مشاهده بودند.

اعتبارسنجی نهایی این مرحله ۳۱ تست موفق، type-check، build و diff check است. هشدار حجم chunk تولیدی همچنان غیرمسدودکننده است و به بهینه‌سازی عملکرد منتقل شد.

**گام بعدی:** سخت‌سازی PWA و آماده‌سازی APK، شامل migration، backup/restore، service worker، offline و آزمون موبایل.


## ۱۴۰۵/۰۶/۳۱ — آماده‌سازی زیرساخت APK و تفکیک اپ مشتری

زیرساخت Capacitor برای APK مالک کارگاه آماده شد. `capacitor.config.ts` با شناسهٔ مستقل `ir.workshop.accounting`، مسیر build وب و سیاست عدم mixed content اضافه شد. وابستگی‌های Capacitor و فرمان‌های `android:init`، `android:sync` و `android:open` به package اضافه شدند.

محیط فعلی Java دارد، اما Android SDK و `adb` ندارد؛ بنابراین ایجاد پوشهٔ native Android و build نهایی APK به محیط دارای Android Studio/SDK منتقل شد. این موضوع مانع build وب و PWA نیست.

ممیزی معماری اپ مشتری تکمیل شد. اپ مشتری باید برنامه‌ای جدا با applicationId جدا، backend احراز هویت‌شده و Row-Level Security باشد. استفاده از APK مالک، localStorage، لینک دارای partyId یا فایل JSON کامل کارگاه برای مشتری مجاز نیست. قرارداد کامل در `docs/APK-AND-CUSTOMER-APP-ARCHITECTURE.md` ثبت شد.

**گام بعدی:** نصب Android SDK در محیط build، اجرای `android:init` و ساخت APK debug؛ هم‌زمان طراحی schema و policyهای backend مشتری با یک tenant آزمایشی.


## ۱۴۰۵/۰۶/۳۱ — تصمیم توقف انتشار APK تا پایان آزمون واقعی

کاربر تصمیم گرفت پیش از ساخت و انتشار APK release، چند دوره با نسخهٔ فعلی وب/PWA کار کند و اشکالات، ابهام‌ها و اصلاحات قابل مشاهده را ثبت و اعمال کند. بنابراین پوشهٔ Android و زیرساخت Capacitor حفظ می‌شوند، اما انتشار APK به مرحلهٔ بعد از آزمون پذیرش واقعی منتقل شد.

APK مالک کارگاه در همین مخزن نگهداری خواهد شد تا موتور حسابداری، تست‌ها، migration و پوستهٔ Android یک منبع نسخه‌گذاری داشته باشند. اپ مشتری در آینده مخزن جدا و معماری مستقل خواهد داشت؛ زیرا فقط‌نمایش مشتری باید با Auth، API و RLS امن اجرا شود و نباید bundle یا localStorage برنامهٔ مالک را به ارث ببرد.

سیاست update شامل versionCode افزایشی، signing key ثابت، backup قبل از migration، بازسازی ledger پس از migration و انتشار رسمی از کانال امضاشده است. remote code loading برای نسخهٔ حسابداری فعال نمی‌شود.

**گام جاری:** دورهٔ استفادهٔ واقعی با نسخهٔ وب/PWA، ثبت ایرادها بر اساس تاریخ شمسی و مرجع فاکتور/چک، سپس اصلاح و آزمون مجدد پیش از هر APK release.


## ۱۴۰۵/۰۶/۳۱ — ممیزی عمیق پارامترها، تراکنش‌ها و چاپ A4

ممیزی عمیق ارتباط مدل‌ها و صفحات انجام شد. مسیرهای تولید، بسته‌های تو‌در‌تو، مصرف و بهای بچ، تبدیل واحد پایه، قیمت فروش، FIFO فاکتورها و چک‌ها، پرداخت خرید، تعهد شریک، دفتر موجودی، دفتر نقدی، انتقال حساب، گزارش تطبیق و backup بررسی شدند. نتیجهٔ اجرایی این بود که چاپ عمومی صفحه قابل اتکا نیست؛ بنابراین پنج مسیر چاپ اصلی به scope مستقل A4 منتقل شدند.

یک خطای حسابداری در رویداد پرداخت خرید اصلاح شد: پرداخت نقدی/بانکی خروج وجه است و باید در دفتر نقدی منفی باشد. schema اکنون ۵ است و migration داده‌های قدیمی مثبت را اصلاح می‌کند. این migration فقط جهت رویداد ناسازگار را اصلاح می‌کند و برای رویدادهای مثبت دریافت یا opening دست‌کاری انجام نمی‌دهد.

برچسب‌های گزارش‌ها نیز اصلاح شدند تا قیمت پایهٔ فروش با بهای تمام‌شده یا سود ناخالص قطعی اشتباه نشود. بهای واقعی تولید همچنان از snapshot و `unitCost` بچ‌ها می‌آید و قیمت فروش از تاریخچهٔ قیمت/ورودی دستی مستقل است.

اعتبارسنجی پس از اصلاح: ۳۲ تست موفق، type-check موفق، build تولیدی موفق و diff check موفق. هشدار bundle بزرگ باقی است و در مرحلهٔ بهینه‌سازی performance پیگیری می‌شود.

**گام بعدی پیشنهادی:** دورهٔ استفادهٔ واقعی با ثبت سناریوهای روزانه، سپس افزودن fixture یکپارچهٔ end-to-end برای خرید، پرداخت چندردیفی، خرج‌کردن چک مشتری، چک شریک، reversal، فروش و بازسازی ledger؛ پس از آن تصمیم نهایی دربارهٔ انتشار APK گرفته شود.


## ۱۴۰۵/۰۶/۳۱ — تکمیل آزمون یکپارچهٔ خرید، چک و reversal

fixture یکپارچهٔ عملیات در تست هسته اضافه و تأیید شد. سناریو دو فاکتور خرید تأمین‌کننده را با سه پرداخت پوشش می‌دهد: چک مشتری، پرداخت نقدی و چک شریک. تخصیص FIFO، رویداد خروج نقدی، رسیدن چک شریک به تاریخ جلالی سررسید، حذف فاکتور اول، بازگشت چک مشتری به وضعیت «نزد ما»، reversal پرداخت نقدی و ابطال/reversal تعهد شریک بررسی شدند.

## ۱۴۰۵/۰۶/۳۱ — رفع باگ ثبت فاکتور با تخفیف کامل

## ۱۴۰۵/۰۷/۰۱ — سخت‌سازی Supplier Directory

اعتبارسنجی این مرحله باید شامل تست round-trip backup، رد فایل نامعتبر، رد مقایسهٔ ناهم‌واحد، type-check، build و diff check باشد. گام بعدی پیشنهادی پس از آزمون دستی: ماتریس امتیازدهی وزنی کیفیت/قیمت/تحویل/ریسک و سپس export CSV یا گزارش مقایسهٔ چاپی.


اعتبارسنجی نهایی مرحلهٔ سخت‌سازی با **۴۱ تست موفق**، type-check موفق، build تولیدی موفق و diff check موفق انجام شد. دو failure اولیه از فرض نادرست تست دربارهٔ مبنای مقایسه بودند و با تفکیک `quoteCount`/`comparableQuoteCount` و تثبیت قرارداد «جدیدترین quotation به‌عنوان basis» اصلاح شدند.


## ۱۴۰۵/۰۷/۰۱ — تحقیق راه آیندهٔ APK، backup و اپ مشتری

تحقیق معماری آینده انجام شد و در `docs/APK-FUTURE-ROADMAP-RESEARCH.md` ثبت شد. نتیجهٔ اصلی این است که APK release تا پایان دورهٔ استفادهٔ واقعی و تکمیل قرارداد unified backup متوقف بماند.

پشتیبان Supplier Directory عمداً مستقل طراحی شده است، چون دفتر sourcing الزاماً خرید و بدهی حسابداری نیست. بااین‌حال حفاظت کامل باید «یکپارچه اما مستقل» باشد: یک envelope نسخه‌دار باید بخش `accounting` و `vendorDirectory` را با هم داشته باشد و export مستقل Supplier Directory نیز حفظ شود.

وضعیت فعلی هنوز این هدف را کامل نکرده است: upload فعلی Google Drive عمدتاً `exportPayload(state)` حسابداری را ارسال می‌کند و Supplier Directory فقط export مستقل/localStorage دارد. اتصال Drive فعلی در وب access token کوتاه‌عمر و scope موجود دارد و backup خودکار پس از بسته‌شدن برنامه تضمین نمی‌شود. این مورد به‌عنوان فاز صفر پیش از APK ثبت شد و نباید در مستندات به‌عنوان قابلیت تکمیل‌شده معرفی شود.

راهبرد تحقیق‌شده: AAB با Play App Signing و rollout مرحله‌ای کانال اصلی Android باشد؛ APK هم‌امضا فقط برای QA/MDM/direct distribution کنترل‌شده استفاده شود؛ OTA در نسخهٔ اول خاموش بماند؛ PWA با prompt update و migration کنترل‌شده اجرا شود؛ اپ مشتری در repository جدا و با backend چندمستاجری، membership زنده و RLS فقط‌خواندنی ساخته شود.


## ۱۴۰۵/۰۷/۰۱ — تکمیل فاز صفر unified backup

فاز صفر roadmap APK تکمیل شد. فایل `client/src/lib/backup.ts` قرارداد unified backup v1 را پیاده می‌کند و شامل حسابداری و Supplier Directory است. Home در دانلود محلی، upload و restore Drive، import فایل و خروجی JSON گزارش‌ها از این قرارداد استفاده می‌کند.

سازگاری backward حفظ شد: backupهای قدیمی accounting-only قابل import هستند و چون section تأمین‌کنندگان ندارند، اطلاعات فعلی Supplier Directory را تغییر نمی‌دهند. restore unified هر دو دفتر را بازسازی می‌کند. اعتبارسنجی نهایی: ۴۳ تست موفق، type-check، build و diff check.

گام بعدی پیشنهادی، سخت‌سازی restore است: snapshot خودکار پیش از restore، checksum و اعتبارسنجی تعداد رکوردها، سپس صف backup و OAuth native برای APK.


## ۱۴۰۵/۰۷/۰۱ — تکمیل سخت‌سازی restore

پیش از restore از فایل، متن یا Google Drive، payload واردشده کامل validate می‌شود. unified backup دارای checksum sectionهای حسابداری و تأمین‌کنندگان و manifest شمارنده است؛ دادهٔ دستکاری‌شده یا ناقص قبل از تغییر state رد می‌شود. پس از validation و پیش از commit، snapshot فعلی در localStorage ذخیره می‌شود و حداکثر سه نسخه نگه داشته می‌شود.

این snapshot هنوز UI بازیابی مستقل ندارد و checksum رمزنگاری نیست. گام بعدی پیشنهادی: صفحهٔ مدیریت snapshotهای محلی و سپس encryption/secure storage در APK.

صفحهٔ پشتیبان و بازیابی فهرست snapshotهای محلی را با تاریخ، ساعت و حجم نشان می‌دهد. عملیات بازیابی و حذف با تأیید انجام می‌شود. Home پس از ایجاد snapshot یا حذف آن فهرست را تازه می‌کند. مسیر restore snapshot از همان checksum، manifest، migration و rebuild حسابداری استفاده می‌کند.

اعتبارسنجی نهایی: ۴۵ تست موفق، type-check، build و diff check. گام بعدی پیشنهادی، آزمون اجرایی UI در preview و سپس طراحی صف backup برای APK است.

## ۱۴۰۵/۰۷/۰۱ — افزودن رمز عبور و PIN محلی

در صفحهٔ تنظیمات، بخش «حفاظت از دستگاه» اضافه شد. کاربر می‌تواند رمز عبور حداقل ۸ نویسه، PIN چهار تا هشت رقمی، یا هر دو را تعریف کند. هنگام بازشدن برنامه، ورود با هرکدام از روش‌های فعال پذیرفته می‌شود. امکان حذف جداگانهٔ رمز عبور یا PIN نیز وجود دارد.

هیچ‌یک از رمزها به‌صورت متن ساده ذخیره نمی‌شود. `client/src/lib/security.ts` با Web Crypto و PBKDF2/SHA-256، salt تصادفی ۱۶ بایتی و ۱۲۰٬۰۰۰ iteration، hash credential را تولید و در `settings.security` نگهداری می‌کند. تنظیمات قبلی بدون credential همچنان معتبرند و بدون قفل باز می‌شوند؛ migration اختصاصی برای آن‌ها لازم نیست. برای backup، hash و salt قابل انتقال‌اند اما خود فایل backup رمزگذاری‌شده نیست.

این قابلیت «قفل محلی همین مرورگر/دستگاه» است و جایگزین احراز هویت سرور، رمزگذاری backup، OAuth یا پرتال امن مشتری نیست. اگر کاربر رمز و PIN را فراموش کند، مسیر بازیابی باید از backup قابل اعتماد یا حذف دستی دادهٔ محلی انجام شود؛ هیچ master password در برنامه تعبیه نشده است.

اعتبارسنجی این مرحله: ۵ فایل تست و ۴۸ تست موفق، `pnpm check` موفق و `pnpm build` موفق. هشدار chunk بزرگ قبلی همچنان غیرمسدودکننده است.


## ۱۴۰۵/۰۷/۰۱ — مرزبندی امنیت محلی و backup

پس از افزودن قفل محلی، قرارداد backup سخت‌سازی شد: `settings.security` شامل salt/hash رمز و PIN از unified backup حذف می‌شود. بنابراین credential محلی نه در فایل backup قرار می‌گیرد و نه با restore به دستگاه دیگر منتقل می‌شود. عبارت قبلی دربارهٔ قابل‌انتقال‌بودن hash/salt credential برای backup دیگر معتبر نیست و این تصمیم جدید مرجع است. backup همچنان رمزگذاری‌شده نیست و باید فایل حساس تلقی شود؛ encryption و secure storage native در فاز APK باقی می‌ماند.

اعتبارسنجی این مرحله: ۴۹ تست موفق، `pnpm check` موفق و `pnpm build` موفق.


## ۱۴۰۵/۰۷/۰۱ — سخت‌سازی restore برای backupهای قدیمی

کنترل مرزبندی امنیت فقط برای backupهای جدید کافی نبود. مسیر `importUnifiedPayload` اکنون پس از import هر دو نوع unified و legacy، `settings.security` را حذف می‌کند؛ بنابراین حتی فایل‌هایی که پیش از اصلاح، hash/salt رمز یا PIN محلی را در خود داشتند، هنگام restore قفل دستگاه مبدأ را منتقل نمی‌کنند. آزمون regression این سناریوی legacy را نیز پوشش می‌دهد.

نتیجهٔ نهایی مرحله: ۵۰ تست موفق، type-check موفق و build موفق.


## ۱۴۰۵/۰۷/۰۱ — fixture یکپارچهٔ سناریوی کارگاه

برای عبور از تست‌های صرفاً واحدی، فایل `client/src/lib/integration.test.ts` به‌عنوان fixture غیرحساس عملیاتی اضافه شد. سناریو شامل ایجاد مادهٔ اولیه و محصول، اجرای تولید ۱۰ عدد، کاهش موجودی ماده، افزایش موجودی محصول، ثبت فاکتور فروش، دریافت چک مشتری، تخصیص کامل FIFO، سپس export/import unified backup است. آزمون در پایان کنترل می‌کند که وضعیت تسویه فاکتور، موجودی محصول، رکورد تولید و مرزبندی credential محلی پس از restore حفظ شده‌اند.

این fixture دادهٔ واقعی یا credential ندارد و برای regression مداوم قابل تکرار است. نتیجهٔ مرحله: ۶ فایل تست و ۵۱ تست موفق تا این نقطه. گام بعدی باید fixture مشابه برای خرید چکی/پرداخت تأمین‌کننده، reversal فاکتور و مغایرت حساب نقدی اضافه کند تا چرخهٔ بدهی و reversal نیز end-to-end پوشش داده شود.


## ۱۴۰۵/۰۷/۰۲ — آزمون قراردادی PWA و service worker

بازبینی سوابق نشان داد چرخهٔ خرید چکی، چک مشتری، چک شریک، پرداخت نقدی، reversal و مغایرت حساب از قبل در تست یکپارچهٔ `accounting.test.ts` پوشش داده شده است؛ بنابراین مرحلهٔ بعدی به‌درستی به سخت‌سازی مسیر PWA منتقل شد.

فایل `client/src/lib/pwa.test.ts` افزوده شد. این تست قرارداد manifest فارسی/RTL، `start_url` و `scope` نسبی، حالت نصب standalone، آیکون‌های ۱۹۲ و ۵۱۲، نسخه‌گذاری cache service worker، محدودبودن cache پویا به same-origin و نبودن نام/دادهٔ مجموعه‌های مالی در service worker را کنترل می‌کند. داده‌های حسابداری همچنان در localStorage هستند و service worker فقط پوسته و assetهای وب را cache می‌کند.

در اجرای اول، ایراد از مسیر تست بود: Vitest از ریشهٔ مخزن اجرا می‌شود اما assetها در `client/public` قرار دارند. مسیر اصلاح شد و اجرای نهایی با ۷ فایل تست و ۵۴ تست موفق، type-check موفق و build موفق پایان یافت. هشدار حجم chunk همچنان غیرمسدودکننده است.


## ۱۴۰۵/۰۷/۰۲ — سود ظاهری و سود مؤثر در زمان وصول چک

برای هر تخصیص چک فروش، دو شاخص جداگانه اضافه شد. **سود ظاهری** برابر است با مبلغ وصول‌شده منهای بهای تمام‌شدهٔ ثبت‌شده هنگام فروش. **سود مؤثر** برابر است با مبلغ وصول‌شده منهای بهای آخرین بچ تولید همان کالا که تا تاریخ واقعی وصول موجود است. هر دو نرخ بر مبنای بهای مربوط محاسبه می‌شوند، نه بر مبنای مبلغ فروش.

در مدل داده، `InvoiceItem.unitCostAtSale` بهای هر واحد پایه در زمان ثبت فاکتور را نگهداری می‌کند و `Check.collectedDate` تاریخ واقعی وصول را نگهداری می‌کند. تاریخ سررسید و تاریخ دریافت برای سود مؤثر استفاده نمی‌شوند. هنگام تغییر وضعیت چک به «وصول شده»، تاریخ همان روز جلالی ثبت می‌شود؛ هنگام ویرایش صرفاً حساب بانکی، تاریخ وصول قبلی حفظ می‌شود.

تابع `calculateEffectiveProfitForAllocation` هزینهٔ چندقلمی فاکتور را به نسبت اصل تخصیص‌یافته به مبلغ فاکتور سرشکن می‌کند. برای بهای زمان وصول، آخرین `ProductionRecord.unitCost` همان `outputProductId` تا تاریخ وصول انتخاب می‌شود؛ در نبود بچ جدید، بهای ثبت‌شدهٔ زمان فروش fallback است. اگر فاکتور قدیمی بهای زمان فروش نداشته باشد، breakdown در UI نمایش داده نمی‌شود تا سود ساختگی تولید نشود.

در مثال مرجع: چک ۳۳۶٬۰۰۰ تومان، بهای زمان فروش ۱۶۰٬۰۰۰، بهای زمان وصول ۱۸۰٬۰۰۰؛ سود ظاهری ۱۷۶٬۰۰۰ و ۱۱۰٪، سود مؤثر ۱۵۶٬۰۰۰ و ۸۶٫۶۷٪ است. breakdown در آکاردئون فاکتور و آکاردئون چک پس از وصول نمایش داده می‌شود.

اعتبارسنجی این مرحله: ۷ فایل تست و ۵۵ تست موفق، type-check موفق و build موفق.


## ۱۴۰۵/۰۷/۰۲ — گزارش قابل مشاهدهٔ سود هر چک، فاکتور، ماه و سال

در بازبینی UI مشخص شد نمایش قبلی فقط در آکاردئون تخصیص‌ها بود و برای کاربر به‌عنوان گزارش مستقل قابل مشاهده نبود. پنل جدید «گزارش مستقل وصول / سود ظاهری و سود مؤثر» در صفحهٔ «گزارش‌ها» اضافه شد.

این پنل سه سطح دارد: جدول ردیف‌به‌ردیف هر تخصیص وصول‌شده که هم شمارهٔ چک و هم شمارهٔ فاکتور را نشان می‌دهد؛ جدول تجمیع ماهانه بر اساس `collectedDate`؛ و جدول تجمیع سالانه بر اساس همان تاریخ. ستون‌های هر ردیف شامل مبلغ وصول، هزینهٔ دیرکرد، سود ظاهری، درصد ظاهری، سود مؤثر و درصد مؤثر است. برای دادهٔ بدون چک وصول‌شده، پیام روشن و قابل مشاهده نمایش داده می‌شود.

تمام عنوان‌های کاربری و captionهای مرتبط با سود دیرکرد به «هزینهٔ دیرکرد» تغییر کرد تا دیرکرد با سود عملیاتی کالا اشتباه نشود. منطق محاسبهٔ عددی قبلی تغییر نکرد: هزینهٔ دیرکرد از تخصیص FIFO می‌آید و سود کالا از بهای زمان فروش و بهای آخرین تولید تا تاریخ واقعی وصول.

اعتبارسنجی پس از اصلاح سازگاری TypeScript: ۷ فایل تست و ۵۵ تست موفق، type-check موفق و build موفق. هشدار حجم chunk بزرگ موجود است اما مانع انتشار نیست.


## ۱۴۰۵/۰۷/۰۲ — اصلاح چک وصول‌شدهٔ legacy و یکسان‌سازی هزینه دیرکرد

**مشکل مشاهده‌شده:** برخی چک‌های قدیمی با وضعیت «وصول شده» فاقد `collectedDate` بودند و گزارش مستقل فقط از allocationهای ذخیره‌شده استفاده می‌کرد؛ درنتیجه آکاردئون و گزارش برای یک دادهٔ یکسان رفتار متفاوت داشتند.

**اصلاح:** هنگام normalize داده، برای چک وصول‌شده اگر `collectedDate` وجود نداشته باشد، ابتدا تاریخ تراکنش دریافت دارای marker `__check:<id>`، سپس `receivedDate` و در نهایت `dueDate` به‌عنوان fallback استفاده می‌شود. گزارش مستقل نیز مانند آکاردئون‌ها از `settleChecksFIFO` جاری ساخته می‌شود و به allocation قدیمی وابسته نیست.

برای فاکتورهای legacy فاقد `unitCostAtSale`، آخرین رکورد تولید معتبر تا تاریخ فاکتور به‌عنوان بهای زمان فروش استفاده می‌شود. در نتیجه چک قدیمیِ وصول‌شده، در صورت وجود سابقهٔ تولید، سود ظاهری و مؤثر خواهد داشت.

همهٔ labelهای عملیاتی دیرکرد در صفحات، شرایط پرداخت، جدول‌ها و caption موتور به «هزینه دیرکرد» تغییر یافتند. عبارت «سود ظاهری» و «سود مؤثر» فقط برای سود کالا باقی مانده است.

اعتبارسنجی: ۵۵ تست موفق، type-check موفق و build موفق.


## ۱۴۰۵/۰۷/۰۳ — ممیزی سراسری و پنل سلامت داده

ممیزی سراسری مسیرهای اصلی رابط، فاکتورها، چک‌ها، FIFO، سود، انبار، تولید، backup/restore، PWA و امنیت محلی انجام شد. همهٔ مقصدهای اصلی sidebar به component متناظر متصل‌اند و regression فعلی ۵۶ تست موفق، type-check موفق و build موفق دارد.

گام اجرایی این مرحله افزودن تابع read-only `auditDataIntegrity` و پنل «ممیزی یکپارچگی حسابداری» در صفحهٔ گزارش‌هاست. این پنل شمارهٔ تکراری فاکتور/چک، ارجاع شکستهٔ طرف حساب/کالا/حساب/شرایط پرداخت، تخصیص بیش از سقف، allocation خرید نامعتبر، رویدادهای ledger با مرجع حذف‌شده و اختلاف projection با دفتر رویداد را با شدت خطا/هشدار/اطلاعات نشان می‌دهد. پنل هیچ اصلاح خودکاری انجام نمی‌دهد.

**گام بعدی:** تکمیل projection-first دفتر موجودی با رویدادهای برگشت‌پذیر برای همهٔ مسیرهای خرید، فروش، تولید، اصلاح، ویرایش و حذف؛ سپس اجرای migration با fixture غیرحساس و تبدیل پنل ممیزی به معیار پذیرش release.


## ۱۴۰۵/۰۷/۰۳ — اصلاح خطای کاذب تخصیص شامل هزینه دیرکرد

در آخرین بکاپ واقعی Google Drive (`accounting-workshop-backup-1405-06-29-005.json`) فاکتور ۱۰۱۰ بررسی شد. مبلغ اصل فاکتور `۱۶۲٬۰۰۰٬۰۰۰` تومان، مبلغ تخصیص شامل هزینه دیرکرد `۱۸۸٬۳۳۸٬۰۶۴٫۵۱` تومان و `principalAmount` برابر `۱۶۱٬۹۹۹٬۹۹۹٫۹۹۹۹۹۹۹۷` تومان بود. بنابراین مقایسهٔ قبلی `allocation.amount` با مبلغ فاکتور اشتباه بود؛ `amount` شامل اصل به‌علاوهٔ هزینه دیرکرد است و فقط `principalAmount` باید با سقف فاکتور مقایسه شود.

بررسی تمام رکوردهای بکاپ نشان داد ۱۰ فاکتور همین الگو را دارند و همگی false positive بودند. ممیزی اصلاح شد تا سقف فاکتور را با `principalAmount ?? amount` بسنجد، درحالی‌که سقف چک همچنان با مبلغ واقعی تخصیص شامل هزینه دیرکرد کنترل می‌شود.

همچنین فاکتور ۱۰۱۰ در بکاپ به‌علت اختلاف اعشاری بسیار کوچک بین مبلغ اصل و `paidAmount` با وضعیت «تسویه جزئی» ذخیره شده بود. normalizeState اکنون اختلاف حداکثر `۰٫۰۱` را باقیماندهٔ واقعی تلقی نمی‌کند و چنین فاکتوری را «تسویه شده» می‌کند. این اصلاح فقط وضعیت را canonical می‌کند و مبلغ مالی را تغییر نمی‌دهد.

Regression مخصوص فاکتور ۱۰۱۰ اضافه شد؛ مجموع تست‌ها پس از اصلاح ۵۷ مورد موفق است.


## ۱۴۰۵/۰۷/۰۳ — سازوکار مستقل حقوق و دستمزد

صفحهٔ مستقل «حقوق و دستمزد» به منوی اصلی اضافه شد. این صفحه دو حالت دارد:

1. **پرداخت‌شده:** با ثبت رکورد، حساب بانک یا صندوق به‌اندازهٔ مبلغ کاهش می‌یابد و یک تراکنش با نوع `پرداخت حقوق` و خروج وجه در دفتر نقدینگی ایجاد می‌شود.
2. **پرداختنی:** فقط بدهی حقوق در دفتر حقوق ثبت می‌شود و تا زمان پرداخت، حساب بانک/صندوق و حساب شخص تغییری نمی‌کند. با دکمهٔ «پرداخت» حساب انتخابی کاهش یافته و رکورد به پرداخت‌شده تبدیل می‌شود.

`employeeName` و `personId` فقط برای گزارش و اتصال اختیاری به فهرست کارگران هستند. تراکنش حقوق `partyId` ندارد؛ بنابراین ثبت یا پرداخت حقوق، شخص را بدهکار یا طلبکار نمی‌کند. این از «مساعده/پرداخت به شریک» جداست و نباید با آن ثبت شود.

هر رکورد شامل دوره، تاریخ، نام دریافت‌کننده، مبلغ، وضعیت، حساب پرداخت‌کننده، شناسه تراکنش، تاریخ پرداخت و توضیح است. ابطال رکورد پرداخت‌شده، تراکنش را باطل و ماندهٔ حساب را معکوس می‌کند. سوابق `payrollRecords` داخل backup یکپارچه ذخیره و در migrationهای قدیمی به آرایهٔ خالی تبدیل می‌شوند.

این مرحله عمداً کسورات قانونی، بیمه، مالیات، و محاسبهٔ فیش پیچیده را پیاده‌سازی نمی‌کند؛ این موارد باید در مرحلهٔ جداگانه و با مدل حقوق ناخالص/خالص و حساب‌های پرداختنی طراحی شوند.


## ۱۴۰۵/۰۷/۰۳ — اتصال حقوق به کارگر، کارمند و شریک

دفتر اشخاص اکنون نقش «کارمند» را نیز مانند «کارگر» و «شریک» پشتیبانی می‌کند. فرم حقوق از بین اشخاص دارای هرکدام از این سه نقش، شخص را انتخاب و `personId` را در `payrollRecords` ذخیره می‌کند. نام و نقش فعلی شخص در جدول حقوق از دفتر اشخاص خوانده می‌شود؛ بنابراین اصلاح نام شخص در صفحهٔ طرف‌حساب‌ها در مشاهدهٔ سوابق حقوق نیز منعکس می‌شود.

این اتصال فقط رابطهٔ اطلاعاتی است و `partyId` تراکنش حقوق همچنان خالی می‌ماند. پس پرداخت حقوقِ کارگر، کارمند یا شریک، ماندهٔ طلب/بدهی او را تغییر نمی‌دهد. ارجاع‌های شکستهٔ `personId`، حساب پرداخت و تراکنش مرتبط اکنون توسط `auditDataIntegrity` گزارش می‌شوند.

## ۱۴۰۵/۰۷/۰۳ — گزارش‌گیری دفتر حقوق
دفتر حقوق اکنون فیلترهای شخص، نقش، وضعیت و دوره دارد. رکوردهای باطل‌شده در فهرست عملیاتی و خلاصهٔ دوره‌ای نمایش داده نمی‌شوند. خلاصهٔ دوره‌ای برای حداکثر شش دورهٔ اخیر، تعداد رکورد، مجموع پرداخت‌شده، مجموع پرداختنی و جمع تعهد دوره را نشان می‌دهد. کارت «رکوردهای فعال» تعداد نتیجهٔ فیلتر فعلی را نمایش می‌دهد. فیلترها در موبایل به چیدمان دو ستونه تبدیل می‌شوند.

## ۱۴۰۵/۰۷/۰۳ — کارمزد انتقال از حساب مبدأ

برای انتقال بین دو حساب، `Transaction.amount` فقط اصل مبلغ است و `feeAmount` کارمزد مستقل است. اصل مبلغ کامل به حساب مقصد می‌رسد؛ از حساب مبدأ دو خروج ثبت می‌شود: خروج اصل مبلغ و خروج هزینهٔ کارمزد. کارمزد به مبلغ فاکتور، بدهی طرف‌حساب یا مبلغ دریافتی مقصد اضافه نمی‌شود.

فرم عملیات مالی کارمزد را با مقدار صفر یا مبلغ دستی می‌پذیرد و آن را با `feeSource: دستی` ذخیره می‌کند. در دفتر نقدی، رویداد انتقال اصل و رویداد هزینهٔ بانکی جدا ثبت می‌شوند. ویرایش کارمزد رویدادهای قبلی را با reversal معکوس و رویداد جدید را ثبت می‌کند؛ بنابراین اصلاح کارمزد موجودی projection و دفتر رویداد را هم‌زمان حفظ می‌کند. ممیزی، کارمزد منفی، کارمزد بدون انتقال و کارمزد بدون حساب مبدأ را گزارش می‌کند.

آزمون سناریوی انتقال ۱۰۰ با کارمزد ۵ از موجودی ۱۰۰۰، دریافت کامل ۱۰۰ در مقصد، اصلاح کارمزد از ۵ به ۸ و حذف مغایرت دفتر نقدی انجام شد. مجموع تست‌ها ۶۲ مورد موفق، type-check و build موفق هستند.

## ۱۴۰۵/۰۷/۰۳ — تعرفهٔ خودکار کارمزد انتقال

صفحهٔ «تنظیمات» اکنون بخش قابل مشاهدهٔ «تعرفهٔ خودکار کارمزد انتقال» دارد. هر تعرفه شامل نام، حساب مبدأ اختیاری، درصد، مبلغ ثابت، حداقل، حداکثر و وضعیت فعال/غیرفعال است. تعرفهٔ اختصاصی حساب مبدأ بر تعرفهٔ عمومی مقدم است. تعرفه‌ها در `settings.bankFeeRules` ذخیره و همراه بکاپ منتقل می‌شوند.

در صفحهٔ «عملیات مالی»، هنگام انتخاب «انتقال بین حساب‌ها»، مبلغ کارمزد بر اساس مبلغ انتقال و حساب مبدأ خودکار در فیلد کارمزد قرار می‌گیرد و نام تعرفه و مبلغ پیشنهادی زیر همان فیلد نمایش داده می‌شود. کاربر می‌تواند مبلغ را اصلاح کند؛ در این حالت منبع تراکنش «دستی» ثبت می‌شود. اگر مقدار خودکار تغییر نکند، منبع «تعرفه» ثبت می‌شود. مبلغ اصل انتقال همیشه کامل به مقصد می‌رسد و کارمزد فقط از مبدأ کسر می‌شود.

## ۱۴۰۵/۰۷/۰۳ — یکپارچه‌سازی سراسری کارمزد و بالانس بانک

ممیزی مسیرهای نقدی نشان داد کارمزد فقط نباید به «انتقال بین حساب‌ها» محدود باشد. سازوکار واحد اکنون در چهار مسیر اعمال می‌شود: انتقال بین حساب‌ها، پرداخت خرید از بانک/صندوق، پرداخت حقوق از بانک/صندوق و وصول چک به حساب بانکی/صندوق. در همهٔ موارد اصل معامله جدا از کارمزد ثبت می‌شود و کارمزد به‌عنوان رویداد هزینهٔ مستقل از همان حساب کسرکننده در `cashEvents` ذخیره می‌شود.

در فرم فاکتور خرید، ردیف‌های پرداخت نقدی و حساب داخلی فیلد کارمزد دارند و با تغییر مبلغ یا حساب، تعرفهٔ فعال پیشنهاد می‌شود. در فرم حقوق، هنگام انتخاب حساب و تغییر مبلغ، کارمزد پیشنهاد می‌شود؛ حقوق پرداختنی تا زمان پرداخت کارمزد ندارد. در فرم چک، کارمزد وصول ثبت می‌شود و در زمان وصول، رویداد دریافت اصل و رویداد هزینهٔ بانکی جداگانه ایجاد می‌گردد. اصلاح یا برگشت چک، پرداخت خرید و تراکنش، رویدادهای قبلی را با reversal خنثی می‌کند.

صفحهٔ بانک‌ها و صندوق‌ها اکنون تغییر موجودی اولیه/اصلاحی را نیز در قالب رویداد append-only `account_balance_adjustment` ثبت می‌کند. در `commitState` projection حساب‌ها از دفتر رویداد نقدی بازسازی می‌شود تا موجودی ثبت‌شده و موجودی ledger پس از کارمزد هم‌تراز بمانند. بنابراین برای مغایرت صورت‌حساب بانک، کاربر می‌تواند اختلاف را در صفحهٔ بانک‌ها و صندوق‌ها با مقدار اصلاحی مثبت یا منفی ثبت کند؛ این اصلاح اصل معاملات قبلی را تغییر نمی‌دهد.

سناریوهای آزموده‌شده شامل انتقال ۱۰۰ با کارمزد ۵، پرداخت خرید ۱۰۰ با کارمزد ۷، وصول چک ۱۰۰ با کارمزد ۳، اصلاح کارمزد انتقال از ۵ به ۸، برگشت چک، حذف/اصلاح پرداخت خرید، و اصلاح ماندهٔ حساب است. در همهٔ سناریوها اصل مبلغ مقصد/تأمین‌کننده/دریافت چک مستقل از کارمزد باقی می‌ماند و projection نقدی با ماندهٔ حساب اختلاف ندارد.

**گام بعدی:** دورهٔ آزمون پذیرش واقعی روی URL عمومی، شامل ورود دادهٔ غیرحساس، reload، offline/PWA cache، backup/restore تومان و کنترل مسیرهای فاکتور، چک، تولید و مغایرت؛ سپس ثبت هر اصلاح به‌صورت commit و ورودی append-only.


## ۱۴۰۵/۰۷/۰۳ — ثبت بدهی قدیمی تأمین‌کننده بدون افزایش موجودی

**درخواست کاربر:** رزین پلی‌استر قبلاً از یک تأمین‌کننده تهیه و مصرف شده و اکنون در انبار نیست، اما مبلغ آن هنوز بدهی است؛ کاربر می‌خواهد بدهی را وارد کند و از حساب فعلی پرداخت کند.

**بررسی کد:** گزارش تأمین‌کنندگان بدهی را از `invoices` نوع «خرید» و پرداخت‌ها را از `purchasePayments` محاسبه می‌کند. ثبت «عملیات خرید کالا» موجودی را افزایش می‌دهد و برای این سناریو مناسب نیست. فاکتور خرید می‌تواند ردیف آزاد/خدمت بدون `productId` داشته باشد؛ چنین ردیفی مبلغ و بدهی ایجاد می‌کند اما رویداد ورود کالا و تغییر موجودی ندارد. پرداخت خرید پس از انتخاب حساب، رویداد نقدی/بانکی مستقل ایجاد می‌کند و با FIFO به فاکتورهای خرید همان تأمین‌کننده تخصیص می‌یابد.

**راهکار تأییدشده برای نسخهٔ فعلی:** در «فاکتورها»، فاکتور نوع «خرید» برای همان تأمین‌کننده و تاریخ واقعی/تقریبی ثبت شود؛ در ردیف کالا محصول انتخاب نشود، مقدار ۱ و قیمت واحد برابر مبلغ بدهی وارد شود تا ردیف آزاد/خدمت ایجاد شود؛ پرداخت در مرحلهٔ اول خالی بماند تا بدهی باز ثبت شود. سپس با ویرایش همان فاکتور، در بخش پرداخت خرید روش «نقدی» یا روش حساب بانکی/صندوق موجود، حساب فعلی و مبلغ پرداخت انتخاب و ذخیره شود. این کار بدهی را تسویه و ماندهٔ حساب را کم می‌کند، بدون اینکه موجودی رزین تغییر کند.

**محدودیت:** این راهکار از نظر حسابداری صحیح و بدون اثر انبار است، اما برچسب ردیف آزاد ممکن است به‌جای «بدهی افتتاحیه تأمین‌کننده» نمایش داده شود. برای UX بهتر، قابلیت مستقل «ماندهٔ افتتاحیه/بدهی قبلی تأمین‌کننده بدون کالا» در backlog باقی می‌ماند.

**کنترل پس از ثبت:** گزارش تأمین‌کنندگان باید مبلغ فاکتور و پرداخت را نشان دهد و مانده صفر شود؛ گزارش گردش نقدی/بانک باید پرداخت خرید را نشان دهد؛ موجودی رزین و رویدادهای موجودی نباید تغییر کنند. واحد مبلغ طبق قرارداد پروژه تومان است و نباید تبدیل ریال/تومان انجام شود.

**گام بعدی:** اگر استفاده از این سناریو تکرار می‌شود، فرم رسمی بدهی افتتاحیه تأمین‌کننده با ثبت ledger و بدون ردیف صوری طراحی و با تست پذیرش اضافه شود.

**درخواست کاربر:** در مرتب‌سازی فاکتورها و چک‌ها، جدیدترین رکورد در بالای فهرست باشد؛ برای تعداد بسیار زیاد، فهرست پیچیده نشود و به‌صورت صفحه‌های شماره‌دار مانند ۱، ۲، ۳ نمایش داده شود.

## ۱۴۰۵/۰۷/۰۶ — گزارش چاپی محرمانه و مشتری‌محور فاکتور و چک

**درخواست کاربر:** پرینت فاکتورها و چک‌ها برای ارسال به مشتری باید خلاصهٔ وضعیت باشد؛ سود و اطلاعات خصوصی یا اطلاعات مشتریان دیگر نباید در گزارش باشد. زیر هر فاکتور یا چک، تخصیص‌های مرتبط همراه با تعداد روز ثبت شود و برای جدول‌های عریض امکان چاپ افقی وجود داشته باشد.

**بررسی و ریسک:** چاپ فاکتور از جزئیات همان فاکتور انجام می‌شد، اما جزئیات تخصیص در آن صفحه کامل نبود و برخی اطلاعات سود/هزینه در ردیف‌های تخصیص وجود داشت. چاپ چک‌ها از فهرست عمومی انجام می‌شد و بدون محدودیت مشتری می‌توانست اطلاعات چند مشتری را در یک گزارش قرار دهد؛ همچنین صفحه‌بندی نباید باعث ناقص شدن گزارش چاپی شود.

**اصلاح اجراشده:**
- جزئیات «چک‌های تخصیص‌یافته به این فاکتور» به زیر فاکتور چاپی اضافه شد: شماره، وضعیت، سررسید، مبلغ تخصیص و تعداد روز.
- در گزارش چاپی فاکتور و چک، هزینهٔ دیرکرد، سود ظاهری، سود مؤثر و درصدهای سود با نشانگر `print-private` حذف می‌شوند؛ این اطلاعات در رابط داخلی همچنان موجود است.
- چاپ چک به انتخاب صریح یک مشتری وابسته شد. اگر «همه مشتری‌ها» انتخاب شده باشد، چاپ متوقف و پیام محرمانگی نمایش داده می‌شود.
- گزارش چک فقط رکوردهای همان مشتری و فیلترهای انتخاب‌شده را چاپ می‌کند و همهٔ رکوردهای matching را چاپ می‌کند، نه فقط صفحهٔ جاری ۲۵ ردیفی. تخصیص‌های هر چک پیش از چاپ باز می‌شوند.
- ستون حساب/مرجع داخلی و ستون عملیات از گزارش چاپی حذف شدند. وضعیت، شماره، تاریخ دریافت، سررسید، مبلغ و تخصیص‌ها باقی می‌مانند.
- دو حالت چاپ portrait و landscape برای فاکتور و گزارش چک اضافه شد؛ landscape با `@page landscape` و اندازهٔ A4 افقی فعال می‌شود.

**حفاظت از داده:** هیچ داده‌ای حذف یا تغییر نمی‌کند؛ حذف اطلاعات فقط در media print است. منطق ledger، FIFO، موجودی، سود و ذخیره‌سازی دست‌نخورده باقی مانده است.

**آزمون:** `pnpm exec tsc --noEmit --pretty false` موفق؛ `pnpm exec vitest run` با ۱۰ فایل و ۸۵ تست موفق؛ `pnpm build` موفق؛ `git diff --check` بدون خطا. هشدار chunk بزرگ Vite غیرمسدودکننده است.

**گام بعدی:** انتشار commit و بررسی URL عمومی. در استفادهٔ واقعی باید پیش از چاپ گزارش چک، مشتری موردنظر انتخاب شود؛ این محدودیت عمدی و برای جلوگیری از افشای اطلاعات مشتریان دیگر است.


## ۱۴۰۵/۰۷/۰۷ — اصلاح تخصیص چک برگشتی، دیرکرد و قیمت‌گذاری تولید

**درخواست کاربر:** چک برگشتی نباید تخصیص فاکتور را حذف یا مبلغ فاکتور را تغییر دهد؛ دیرکرد باید فقط برای اطلاع از فاصلهٔ سررسید تا وصول واقعی محاسبه شود؛ بهای بستهٔ تولیدی باید از فرمول بسته و با تبدیل واحد وارد فرمول بالادست شود؛ برای بخشی از تولید امکان ساخت سطر قیمت جدید وجود داشته باشد؛ چاپ افقی فاکتور نیز فعال بماند.

**نقطهٔ بازگشت:** پیش از تغییر، tag و branch `checkpoint/pre-returned-check-and-production-price-fix-1405-07-06` و `backup/pre-returned-check-and-production-price-fix-1405-07-06` روی commit پایدار قبلی ساخته شد.

**بررسی ریشه‌ای:** `settleChecksFIFO` وضعیت «برگشتی» را از فهرست eligible حذف می‌کرد؛ بنابراین `rebuildCheckAllocations` می‌توانست تخصیص موجود به فاکتور را از بین ببرد. در محاسبهٔ دیرکرد، فاصلهٔ تاریخ فاکتور تا سررسید به‌عنوان روز دیرکرد استفاده می‌شد، در حالی‌که چک وصول‌نشده نباید هزینهٔ دیرکرد ایجاد کند. در `executeProduction` برای محصول «بسته تولید» فقط قیمت مستقل محصول خوانده می‌شد؛ چون قیمت آن معمولاً صفر است، هزینهٔ بسته در فرمول بالادست صفر می‌شد.

**اصلاح اجراشده:** «برگشتی» تا زمان «باطل»، «عودت داده شده»، «جایگزین شده» یا «خرج شده» در FIFO باقی می‌ماند. `calculateLateProfit` فقط در صورت وجود `collectedDate` تعداد روز را از `dueDate` تا `collectedDate` می‌گیرد؛ پیش از وصول روز و هزینهٔ دیرکرد صفر است. بهای مواد در تولید به‌صورت بازگشتی و بر مبنای واحد پایه محاسبه می‌شود و قیمت مستقل فقط fallback است. `calculateCurrentProductionUnitCost` و `refreshProductionRecordPrice` اضافه شدند؛ عملیات قیمت‌گذاری فقط state قیمت را تغییر می‌دهد و موجودی فیزیکی یا ledger را دو برابر نمی‌کند. در دفتر بچ، مقدار بخشی به واحد پایه تبدیل و یک `priceRevisions` append-only با تاریخ، مقدار، بهای واحد و مبلغ کل ساخته می‌شود؛ بنابراین یک بچ می‌تواند سطر اولیه و سطرهای قیمت جدید داشته باشد. پیش‌نمایش UI نیز از همان محاسبهٔ هسته استفاده می‌کند.

**آزمون‌ها:** `pnpm exec tsc --noEmit --pretty false`، `pnpm exec vitest run` با ۱۰ فایل و ۸۷ تست، `pnpm build` و `git diff --check` موفق شدند. تست‌های regression پایداری تخصیص چک برگشتی، صفر بودن دیرکرد قبل از وصول، فاصلهٔ سررسید تا وصول، هزینهٔ بستهٔ تو در تو با قیمت مستقل صفر و ایجاد سطر قیمت بخشی را پوشش می‌دهند.

**محدودیت ثبت‌شده:** سطرهای قیمت جدید، قیمت‌گذاری بخش‌های همان بچ هستند و موجودی فیزیکی جدید ایجاد نمی‌کنند. اتصال تخصیص مقدار فروش به این سطرها در مدل فروش آینده باید از `priceRevisions` استفاده کند.

**تصمیم سازگار با پروژهٔ اصلی:** `exportUnifiedPayload(state, loadVendorDirectory())` بدون تغییر به‌عنوان تنها محتوای پشتیبان استفاده می‌شود. Drive همچنان فایل‌هایی با الگوی `backup-YYYY-MM-DD-NNN.json` را نگه می‌دارد؛ Dropbox فایل مستقل با الگوی `dropbox-backup-YYYY-MM-DD-NNN.json` را در پوشهٔ `/backups/سال/ماه` نگه می‌دارد. بنابراین محل و نام فیزیکی متفاوت است، اما هر دو فایل از یک قرارداد unified backup v1 استفاده می‌کنند و هرکدام با بازیابی دستی یا مستقیم قابل انتقال بین مسیرها هستند.

**اصلاح اجراشده در پروژهٔ اصلی:** `client/src/lib/dropbox.ts` با namespace مستقل `accounting-workshop-pwa:*` اضافه شد تا کلیدها و اتصال این سایت با نصب Cedric تداخل نداشته باشد. `Home.tsx` اکنون اتصال، قطع اتصال، فهرست، ذخیره و بازیابی Dropbox را در صفحهٔ پشتیبان دارد. بازگردانی Dropbox نیز قبل از جایگزینی، از مسیر snapshot و validation فعلی عبور می‌کند.

**نیاز راه‌اندازی کاربر:** در Dropbox App Console یک App از نوع Scoped access / App folder ساخته شود، redirect URI نسخهٔ اصلی برابر `https://rasool083.github.io/accounting-workshop-pwa/` ثبت شود و scopeهای `files.metadata.read`، `files.content.read` و `files.content.write` فعال شوند؛ سپس App key عمومی در کارت Dropbox برنامه وارد شود. هیچ client secret در کد یا backup قرار نمی‌گیرد.

**آزمون:** `pnpm exec tsc --noEmit --pretty false` موفق؛ `pnpm exec vitest run` با ۱۱ فایل و ۹۵ تست موفق؛ `pnpm build` موفق؛ `git diff --check` موفق. هشدار chunk بزرگ Vite غیرمسدودکننده است.

**گام بعدی:** commit و انتشار نسخهٔ اصلی، سپس ثبت App key و آزمون واقعی یک upload/list/restore با دادهٔ آزمایشی غیرحساس؛ پس از تأیید، یک backup واقعی تومان را در هر دو مسیر بررسی کنید.
