# طرح نمایش امن حساب مشتری و پشتیبان موبایل

## نتیجهٔ ممیزی

نسخهٔ فعلی یک PWA ایستا و local-first است. `localStorage` برای یک مالک مناسب است، اما برای نمایش آنلاین حساب هر مشتری کافی نیست؛ زیرا login، API سمت‌سرور، tenant و کنترل دسترسی ردیفی ندارد. `partyId` فقط شناسهٔ طرف حساب است و مجوز امنیتی نیست. ساختن یک HTML با پارامتر مشتری یا لینک مخفی امن نیست، چون هر فرد می‌تواند پارامتر را عوض کند یا فایل داده را دانلود کند.

## گزینه‌های نمایش حساب مشتری

| گزینه                             | مزیت                                  | ضعف امنیتی/فنی                                                  | ارزیابی                         |
| --------------------------------- | ------------------------------------- | --------------------------------------------------------------- | ------------------------------- |
| ارسال JSON برای مشتری             | سریع و بدون زیرساخت                   | کل داده ممکن است افشا شود؛ مناسب پرتال نیست                     | فقط پشتیبان دستی                |
| Google Sheet جدا برای هر مشتری    | قابل مشاهده در گوشی و ساده برای شروع  | کنترل اشتراک‌گذاری و همگام‌سازی دستی؛ امکان اشتراک‌گذاری اشتباه | نمونهٔ آزمایشی محدود            |
| Google Sheet عمومی با لینک تصادفی | بدون login                            | هر دارندهٔ لینک دسترسی دارد و قابل لغو/کنترل کامل نیست          | برای اطلاعات مالی توصیه نمی‌شود |
| PWA نمایشی با token               | تجربهٔ خوب                            | بدون backend و انقضای token امن نیست                            | فقط با backend                  |
| حساب کاربری + database و RLS      | جداسازی واقعی، گزارش زنده و کنترل نقش | نیازمند مهاجرت و پیاده‌سازی backend                             | گزینهٔ پیشنهادی                 |

## معماری پیشنهادی

برای هر مشتری یک `tenant` یا سازمان ایجاد می‌شود. کاربر مشتری با ایمیل/رمز یا Google وارد می‌شود. تمام داده‌های مالی دارای `tenant_id` هستند و database فقط ردیف‌های tenant مجاز را برمی‌گرداند.

مشتری در نسخهٔ فقط‌نمایش می‌تواند این موارد را ببیند:

- فاکتورهای خودش، ریز اقلام و مانده؛
- چک‌های خودش و وضعیت هر چک؛
- تخصیص چک به فاکتورها در دفتر چک و جزئیات فاکتور؛
- بستن ماه و محاسبات سود دیرکرد مربوط به خودش؛
- دریافت آخرین نسخهٔ پشتیبان اختصاصی، بدون دسترسی به دادهٔ مشتریان دیگر.

نقش‌ها باید جدا باشند: `owner`، `accountant` و `customer_viewer`. مشتری فقط `select` دارد و نباید امکان ثبت، ویرایش، حذف، backup کامل یا مشاهدهٔ تنظیمات و مشتریان دیگر را داشته باشد.

## مدل دادهٔ حداقلی

```text
organizations(id, name)
organization_members(user_id, organization_id, role)
people(id, organization_id, ...)
invoices(id, organization_id, party_id, ...)
checks(id, organization_id, party_id, ...)
check_allocations(id, organization_id, invoice_id, check_id, ...)
month_closes(id, organization_id, ...)
```

در هر policy باید هم عضویت کاربر و هم `organization_id` بررسی شود. فیلتر React یا مخفی‌کردن ستون‌ها جای policy database را نمی‌گیرد.

## Google Sheets

Google Sheets می‌تواند برای MVP یک مشتری یا گزارش export‌شده استفاده شود، اما منبع اصلی حسابداری نباشد. برای هر مشتری باید Sheet جدا، دسترسی Viewer محدود به ایمیل همان مشتری، و export فقط ردیف‌های همان مشتری ساخته شود. Sheet عمومی یا لینک ناشناس برای اطلاعات مالی توصیه نمی‌شود. همگام‌سازی باید از backend انجام شود، نه با قرار دادن کلید سرویس در HTML عمومی.

## پشتیبان Google Play / Android

«Google Play» محل ذخیرهٔ عمومی فایل پشتیبان نیست. پشتیبان Android معمولاً در Google Drive حساب دستگاه ذخیره می‌شود و برای دادهٔ app محدودیت و رفتار مخصوص Android دارد. برای PWA نصب‌شده در مرورگر، راهکار قابل اتکای فعلی همان JSON نسخه‌دار در Google Drive است.

اگر بعداً APK ساخته شود، دو مسیر وجود دارد:

1. **پشتیبان داخل Android:** app native باید Auto Backup را پیکربندی کند و دادهٔ قابل پشتیبان را در storage اپ نگه دارد؛ این راهکار برای localStorage مرورگر به‌تنهایی تضمین‌شده نیست.
2. **پشتیبان حسابداری:** خود برنامه JSON رمزگذاری‌شده و نسخه‌دار را به Drive یا backend ارسال کند؛ این مسیر برای بازیابی بین گوشی‌ها قابل فهم‌تر و قابل آزمون‌تر است.

## تصمیم پیشنهادی مرحله‌ای

ابتدا همین اصلاح واکنش‌گرایی و backup دستی/Drive باقی بماند. سپس یک backend چندمشتری با Auth و Row-Level Security ساخته شود و بعد portal فقط‌نمایش مشتری اضافه گردد. Google Sheets فقط به‌عنوان خروجی گزارش یا راهکار MVP محدود استفاده شود. پس از تثبیت portal، APK/TWA ساخته شود و پشتیبان app-level جداگانه تست شود.
