# برنامه و قرارداد مرحلهٔ واحد پول تومان

**تاریخ:** ۱۴۰۵/۰۷/۰۳

**درخواست:** اجرای مرحلهٔ بعد با این تصمیم کسب‌وکاری که واحد عملیاتی حساب‌های کارگاه تومان است و باید پیش‌فرض برنامه باشد.

## تصمیم پایه

واحد پول عملیاتی پیش‌فرض پروژه **تومان** است. در مدل فنی، کد پایدار `IRT` به‌عنوان شناسهٔ تومان و `IRR` به‌عنوان شناسهٔ ریال استفاده می‌شود. متن فارسی برای نمایش از شناسه جداست و هر مقدار مالی باید از یک واحد پول مشخص در metadata سند یا تنظیمات پروژه پیروی کند.

اعداد ذخیره‌شدهٔ فعلی پروژه به‌صورت عدد خام هستند و تا این مرحله مستندات مرجع آن‌ها را تومان می‌دانند. بنابراین تبدیل خودکار همهٔ اعداد از ریال به تومان، حتی اگر از نظر ریاضی ساده به‌نظر برسد، ممنوع است؛ زیرا ممکن است دادهٔ قدیمی کاربر از ابتدا تومان بوده باشد. این مرحله ابتدا قرارداد و dry-run تشخیصی می‌سازد و روی backup واقعی هیچ مقدار مالی را تغییر نمی‌دهد.

## بررسی گزینه‌ها

| گزینه | نتیجه | تصمیم |
|---|---|---|
| نگه‌داشتن متن آزاد مثل «تومان» یا «ریال» | typo، مقایسهٔ ناپایدار و ابهام در backup | رد شد |
| تبدیل همهٔ مقادیر فعلی به ریال | با نیاز واقعی کاربر مغایر و پرریسک | رد شد |
| تبدیل همهٔ مقادیر فعلی به تومان با تقسیم بر ۱۰ | ممکن است دادهٔ فعلی از قبل تومان باشد و مبلغ را خراب کند | رد شد |
| شناسهٔ پایدار IRT/IRR، پیش‌فرض IRT، عدم تبدیل خودکار و dry-run تشخیصی | سازگار، قابل rollback و قابل audit | انتخاب شد |

## دامنهٔ اجرا

در این مرحله enum و helperهای واحد پول، default تومان، normalize سازگار با دادهٔ قدیمی، metadata backup، migration dry-run و گزارش before/after اجرا می‌شود. مقدارهای مالی موجود بدون تصمیم صریح کاربر تغییر نمی‌کنند. متن‌های ثابت «ریال» در UI که با تنظیم پروژه متناقض هستند باید به نمایش واحد تنظیم‌شده متصل شوند.

## قواعد migration

Migration واقعی از نوع تغییر مقدار در این مرحله اجرا نمی‌شود. dry-run فقط فهرست فیلدهای مبلغ، مجموع‌ها، واحد تشخیص‌داده‌شده، تعداد ردیف‌ها و discrepancyها را گزارش می‌کند. گزارش باید روی fixture و backup ساختگی قابل تکرار باشد و checksum قبل و بعد را نشان دهد. اگر واحد صریحی در رکورد قدیمی وجود نداشته باشد، واحد پروژه (`IRT`) به‌عنوان فرض سازگاری ثبت می‌شود، نه اینکه عدد تغییر کند.

## فرمول و مثال

در این مرحله تبدیل مقدار انجام نمی‌شود. اگر در آینده کاربر صریحاً migration ریال به تومان را تصویب کند، قرارداد تبدیل چنین خواهد بود:

```text
تومان = ریال ÷ ۱۰
ریال = تومان × ۱۰
```

مثال ۱۰۰٬۰۰۰ تومان در وضعیت فعلی همان ۱۰۰٬۰۰۰ تومان باقی می‌ماند. فقط در migration صریح ریال به تومان، ۱٬۰۰۰٬۰۰۰ ریال به ۱۰۰٬۰۰۰ تومان تبدیل خواهد شد.

## دروازهٔ پذیرش

عبور از این مرحله مستلزم موفقیت `pnpm check`، full Vitest، harness ۶۰۶حالته، FIFO، backup round-trip، dry-run fixture، integrity audit، build و smoke محلی/عمومی است. هر discrepancy باید یا صفر باشد یا در گزارش با علت و راه‌حل ثبت شود.

**مرحلهٔ بعد پس از این سند:** بررسی تعاملی UI تنظیمات و گزارش‌ها، سپس تصمیم‌گیری جداگانه دربارهٔ اینکه آیا هیچ backup واقعی واقعاً ریالی است یا نه. تا آن زمان تبدیل مقدار مالی ممنوع است.


## نتیجهٔ اجرای مرحله

قرارداد `IRT`/`IRR` اجرا شد. `IRT` و متن «تومان» پیش‌فرض شدند، Settings دیگر هنگام خالی‌بودن فیلد به «ریال» fallback نمی‌کند، و دادهٔ قدیمی بدون currency به‌صورت سازگار تومان فرض می‌شود. داده‌ای که صریحاً «ریال» اعلام کند `IRR` می‌گیرد اما مقدار عددی آن تغییر نمی‌کند.

در backup معمولی metadata واحد پول شامل `code` و `label` شد. در unified backup نیز همین metadata در envelope قرار گرفت. helperهای `normalizeCurrencyCode` و `currencyLabel` یک منبع مشترک برای کد و متن نمایش هستند.

ابزار `scripts/currency-dry-run.ts` روی fixture اجرا شد. این ابزار migration مقداری انجام نمی‌دهد؛ فقط round-trip و invariants را گزارش می‌کند. نتیجه شامل ۲۲ فیلد پولی، مجموع ۴۱۹٬۲۹۰٬۰۰۰، تعداد رکوردهای برابر قبل و بعد، مسیرهای پولی برابر، مقدارهای برابر و `noValueConversion: true` بود. checksum عادی قبل و بعد dry-run هر دو `e97c9c24` بودند.

اعتبارسنجی نهایی: ۱۰ فایل تست و ۸۵ تست موفق، `pnpm check` موفق، harness با ۶۰۶ حالت موفق، FIFO موفق، checksum fixture موفق، build موفق و smoke محلی/عمومی `200 OK`. warning حجم chunk و warningهای pnpm موجود هستند؛ خطای عملکردی ایجاد نکرده‌اند. Prettier نیز بدهی baseline شناخته‌شده دارد.

## مرز مهم برای ادامه

این مرحله عمداً مقدارهای مالی را تقسیم یا ضرب نکرد. برای تشخیص اینکه backup واقعی کارگاه واقعاً ریالی است یا تومانی، باید یک بازبینی داده‌محور و تأیید کاربر انجام شود. تنها پس از آن می‌توان migration واقعی ریال به تومان با ضریب ۱۰، preview، backup قبل، rollback و امضای audit اجرا کرد.

## مرحلهٔ بعد

مرحلهٔ بعد «بازبینی واحد پول backup واقعی و migration اختیاری ریال به تومان» است. ابتدا همهٔ backupها بدون تغییر خوانده و با metadata، متن‌ها، اندازهٔ مبالغ و مثال‌های کسب‌وکار مقایسه می‌شوند؛ سپس فقط اگر کاربر صریحاً ریالی‌بودن یک backup را تأیید کند، migration مقداری ساخته و روی کپی اجرا خواهد شد.


## نتیجهٔ اجرای این مرحله

### تغییرات اجراشده

- checkpoint بازگشت `checkpoint/pre-toman-currency-1405-07-03` پیش از تغییر کد ساخته شد.
- شناسهٔ پایدار `IRT` برای تومان و `IRR` برای ریال اضافه شد.
- پیش‌فرض seed و normalize برابر تومان (`IRT`) شد.
- دادهٔ legacy با `currency: "تومان"` یا بدون currency بدون تغییر عددی به `IRT` normalize می‌شود.
- دادهٔ صریح `currency: "ریال"` به `IRR` شناخته می‌شود اما مقدارها تبدیل نمی‌شوند.
- fallback قدیمی فرم Settings که مقدار خالی را به ریال تبدیل می‌کرد حذف شد و انتخاب واحد پول به select محدود تبدیل شد.
- metadata واحد پول به backup معمولی و unified backup اضافه شد.
- برچسب مبلغ در QuickAdd از state فعال پروژه خوانده می‌شود و «ریال» hard-code نیست.
- ابزار `scripts/currency-dry-run.ts` به‌صورت pure و بدون mutation ساخته شد.

### گزارش dry-run

حالت اجرا `diagnostic-dry-run-no-value-conversion` است. نتیجهٔ fixture:

| شاخص | قبل | بعد |
|---|---:|---:|
| فیلد مالی شناسایی‌شده | ۲۲ | ۲۲ |
| مجموع عددی فیلدهای مالی | ۴۱۹٬۲۹۰٬۰۰۰ | ۴۱۹٬۲۹۰٬۰۰۰ |
| تعداد فاکتورها | ۲ | ۲ |
| تعداد ردیف فاکتورها | ۲ | ۲ |
| تعداد تراکنش‌ها | ۱ | ۱ |
| تعداد event نقدی | ۲ | ۲ |
| تعداد event موجودی | ۳ | ۳ |
| checksum state | `4359a60c` | `4359a60c` |

همهٔ invariantها موفق‌اند: مسیرهای مالی، مقدارهای مالی، شمارش رکوردها و no-value-conversion برابر هستند. هیچ دادهٔ واقعی یا backup کاربر تغییر نکرده است.

### اعتبارسنجی نهایی

- `pnpm check`: موفق.
- full Vitest: ۱۰ فایل و ۸۵ تست موفق.
- currency، backup و price/unit focused tests: موفق.
- accounting harness: ۶۰۶ حالت موفق.

### خطای کشف‌شده و راه‌حل

در اجرای اول dry-run، import تابع `checksumJson` از `accounting.ts` انجام شده بود، اما تابع در `backup.ts` قرار دارد. اجرای واقعی خطا را آشکار کرد؛ import اصلاح شد و dry-run با همان fixture موفق شد. این خطا در ابزار تست بود و به داده یا منطق مالی سرایت نکرد.

## مرحلهٔ بعد

مرحلهٔ بعد، بررسی تعاملی همهٔ صفحه‌های مالی و تصمیم‌گیری دربارهٔ backupهای واقعی قدیمی است. تا زمانی که برای یک backup مشخص ثابت نشود که مبالغ آن ریالی هستند، هیچ تقسیم بر ۱۰ یا تبدیل مقداری اجرا نمی‌شود. اگر backup ریالی مشخص شد، ابتدا migration جداگانه با گزارش before/after، checksum، rollback و تأیید کاربر ساخته خواهد شد.


## تصمیم جدید دربارهٔ backupهای Google Drive

طبق اعلام قطعی کاربر، **تمام backupهای موجود در Google Drive تومان هستند**. بنابراین برای این مجموعه هیچ تشخیص مجدد ریال/تومان و هیچ تبدیل مقداری لازم نیست. اعداد backupها باید همان‌گونه که هستند restore شوند و فقط metadata `IRT`/تومان، normalize و integrity check اعمال شود.

مرحلهٔ بعد از این تصمیم، migration ریال به تومان نیست؛ بلکه **آزمون سازگاری restore backup تومان** است: مقایسهٔ checksum و تعداد ردیف‌ها، کنترل فاکتور، پرداخت، چک، حساب، eventهای نقدی/موجودی، FIFO و گزارش‌های مالی قبل و بعد از round-trip.
