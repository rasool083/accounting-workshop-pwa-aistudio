# گزارش ممیزی عمیق مخزن `accounting-workshop-pwa`

**تاریخ بررسی:** ۱۴۰۵/۰۷/۰۲ برابر با 2026-09-24 در محیط بررسی  
**مخزن:** `rasool083/accounting-workshop-pwa`  
**شاخه:** `main`  
**نوع برنامه:** PWA محلی و آفلاین با بسته‌بندی Capacitor برای Android  
**وضعیت داده:** محلی در `localStorage`؛ Google Drive فقط مسیر اختیاری پشتیبان است.

## ۱. خلاصهٔ اجرایی

این پروژه یک دفتر حسابداری عملیاتی برای کارگاه است که در حال حاضر یک برنامهٔ تک‌صفحه‌ای React/TypeScript با Vite است. صفحهٔ اصلی در `client/src/pages/Home.tsx` تقریباً تمام UI حسابداری را در خود دارد و منطق دامنه در `client/src/lib/accounting.ts` متمرکز شده است. دفتر تأمین‌کنندگان و استعلام‌ها عمداً در ماژول جداگانهٔ `vendorDirectory.ts` و کلید مستقل localStorage نگهداری می‌شود تا پاک‌سازی یا مهاجرت حسابداری، دفتر تحقیق خرید را تغییر ندهد.

در زمان بررسی، مسیر ساخت سالم بود، TypeScript بدون خطا بود، هر ۶۶ تست موجود موفق شد و مرورگر هر ۱۶ صفحهٔ منوی اصلی را باز کرد. یک آزمون مصنوعی مستقل نیز **۶۰۶ حالت** را برای تاریخ شمسی، تخفیف، کارمزد بانکی، دیرکرد، پشتیبان حسابداری و تحلیل تأمین‌کنندگان اجرا کرد و همه موفق شدند. این نتیجه نشان می‌دهد هستهٔ مدل در وضعیت فعلی قابل اتکاست، اما سطح تضمین انتشار هنوز با هدف مستندات پروژه فاصله دارد: اسکریپت رسمی `test` وجود ندارد، تست UI و E2E رسمی وجود ندارد، چندین فایل با Prettier ناسازگارند و bundle اصلی بزرگ است.

## ۳. اجرای برنامه و زنجیرهٔ runtime

`client/src/main.tsx`، `App` را mount می‌کند، CSS را وارد می‌کند و در production service worker را ثبت می‌نماید. `App.tsx` به‌ترتیب ErrorBoundary، ThemeProvider و Toaster را می‌سازد و `Home` را نمایش می‌دهد. Router چندصفحه‌ای وجود ندارد؛ navigation با state به نام `activePage` در Home انجام می‌شود. بنابراین URL مستقل برای هر صفحه وجود ندارد و refresh صفحه به همان صفحهٔ انتخاب‌شدهٔ قبلی route نمی‌شود.

Vite با root برابر `client` اجرا می‌شود، aliasهای `@`، `@shared` و `@assets` دارد و در GitHub Actions base path را به `/accounting-workshop-pwa/` تغییر می‌دهد. server فقط bundle تولیدشده را سرو می‌کند. برای native، `capacitor.config.ts` و فولدر `android` وجود دارد.

Service worker نسخهٔ `accounting-workshop-pwa-v3` را cache می‌کند، فقط درخواست‌های GET را مدیریت می‌نماید، navigation را با network-first و سایر assetهای same-origin را با cache-first پاسخ می‌دهد و cacheهای قدیمی را حذف می‌کند. تست PWA اطمینان می‌دهد که localStorage و دادهٔ حسابداری وارد service worker نشده باشد.

## ۵. مدل داده و ارتباط اجزا

`AppState` شامل تنظیمات، اشخاص، کالاها، انبارها، فاکتورها، تاریخچهٔ قیمت، شرایط پرداخت، تراکنش‌ها، چک‌ها، حساب‌ها، audit، رویدادهای موجودی، رویدادهای نقدی، پرداخت‌های خرید، تخصیص‌های payable، چک‌های صادرشده، تعهدات شریک، فرمول‌ها، رکوردهای تولید و حقوق است.

ارتباط‌های اصلی به این صورت است:

```text
Person ──< Invoice ──< InvoiceItem >── Product ──> Warehouse
   │          │             │              │
   │          └──< CheckAllocation >── Check
   │
   ├──< Transaction
   ├──< PayrollRecord
   └──< PriceHistory

ProductionFormula ──< ProductionRecord ──< ProductionMaterialUsage >── Product
Account ──< CashEvent
Product ──< InventoryEvent
Vendor ──< VendorQuote
```

دو projection اصلی وجود دارد: `rebuildInventoryProjection` موجودی را از `inventoryEvents` بازسازی می‌کند و `rebuildCashProjection` ماندهٔ حساب را از `cashEvents` بازسازی می‌نماید. `reconcileLedgerEvents` هنگام تغییر state تلاش می‌کند eventهای لازم را به‌صورت قابل audit اضافه کند. `auditDataIntegrity` شماره‌های تکراری، ارجاع‌های شکسته، over-allocation و اختلاف projection را گزارش می‌کند.

کلیدهای ذخیره‌سازی مهم عبارت‌اند از:

- `accounting-workshop-pwa:v1`: state اصلی حسابداری.
- `accounting-workshop-pwa:vendor-directory:v1`: دفتر مستقل تأمین‌کنندگان.
- `accounting-workshop-pwa:restore-snapshots:v1`: حداکثر سه snapshot پیش از restore.
- کلید جدا برای Google Client ID و credential محلی؛ hash رمز/PIN هرگز در backup صادر نمی‌شود.

## ۶. فرمول‌ها و سیاست‌های محاسباتی

### ۶.۱ مبلغ فاکتور و واحد دوم

طبق قرارداد فعلی:

```text
مبلغ ردیف = مقدار واحد انتخابی × قیمت واحد × نسبت تبدیل به واحد پایه
مقدار پایهٔ انبار = مقدار واحد انتخابی × نسبت تبدیل
مبلغ نهایی = max(0, جمع ردیف‌ها − تخفیف مبلغی)
```

تخفیف منفی به صفر clamp می‌شود و تخفیف بزرگ‌تر از subtotal فقط تا subtotal پذیرفته می‌شود. در نبود قیمت مستقل برای واحد دوم، قیمت پایه از تاریخچهٔ قیمت معتبر تا تاریخ فاکتور خوانده می‌شود.

### ۶.۲ کارمزد انتقال بانکی

```text
کارمزد خام = مبلغ ثابت + مبلغ انتقال × درصد / ۱۰۰
کارمزد نهایی = clamp(کارمزد خام، حداقل، حداکثر)
```

اول rule اختصاصی حساب مبدأ و سپس rule عمومی انتخاب می‌شود. اصل مبلغ کامل به مقصد می‌رسد و کارمزد فقط از مبدأ کسر می‌شود.

### ۶.۳ هزینهٔ دیرکرد و سود وصول

```text
روزها = اختلاف جلالی تاریخ فاکتور/دریافت تا تاریخ سررسید
روزهای مشمول = max(0, روزها − تنفس)
سود دیرکرد = اصل × نرخ پله × روزهای مشمول / مبنای روزشمار
ارزش تسویه = اصل + سود دیرکرد
```

مبنای روزشمار می‌تواند ۳۰، ماه واقعی شمسی یا ۳۶۵ روز باشد. پله‌ها بر اساس `maxDays` مرتب می‌شوند. سود مؤثر گزارش وصول بر اساس تاریخ واقعی وصول چک محاسبه می‌شود، نه صرفاً تاریخ سررسید.

### ۶.۴ FIFO چک و خرید

فاکتورها بر اساس تاریخ فاکتور و چک‌ها بر اساس سررسید مرتب می‌شوند. یک چک نمی‌تواند از فاکتور قدیمی‌تر عبور کند تا زمانی که اصل آن کامل تسویه نشده باشد. تخصیص هر ردیف، مبلغ، اصل، سود و روز را نگه می‌دارد. برای خرید نیز پرداخت‌ها روی قدیمی‌ترین payable قرار می‌گیرند و release باید event نقدی را معکوس کند؛ حذف release تکراری نباید reversal تکراری بسازد.

### ۶.۵ تولید

هزینهٔ هر اجرا از هزینهٔ مواد واقعی مصرف‌شده و سربار تشکیل می‌شود:

```text
هزینهٔ کل = هزینهٔ مواد + هزینهٔ سربار
بهای واحد = هزینهٔ کل / مقدار خروجی پایه
```

تولید مواد را از انبار کسر و محصول خروجی را اضافه می‌کند. بستهٔ نیمه‌آماده در انبار مواد اولیه و دستهٔ بستهٔ تولید قرار می‌گیرد تا در فرمول بعدی مصرف شود. رکورد اجرا باید مستقل از تغییر یا حذف فرمول باقی بماند.

### ۶.۶ دفتر تأمین‌کنندگان

برای هر ماده، همهٔ quoteها شمارش می‌شوند اما میانگین و کمترین قیمت فقط روی quoteهای هم‌ارز از نظر ارز و واحد مقایسه می‌شود. آخرین قیمت و درصد تغییر نسبت به quote قبلی نیز محاسبه می‌شود. کمترین قیمت صرفاً شاخص اولیه است و توصیهٔ خرید تلقی نمی‌شود.

## ۷. مستندات و روش توسعهٔ پروژه

مستندات پروژه فقط توضیح کاربر نیستند؛ عملاً یک حافظهٔ تصمیم و پروتکل ادامهٔ توسعه‌اند. ترتیب مناسب مطالعهٔ آن‌ها این است:

1. `PROJECT-CONTINUITY.md` برای وضعیت و قراردادهای جاری.
2. `CHAT-CONTINUITY-PROTOCOL.md` برای انتقال زمینه بین نشست‌ها.
3. `DECISION-LOG.md` برای تصمیم‌های قطعی و ریسک‌های باز.
4. `CHANGELOG.md` برای علت تغییرات مرحله‌ای.
5. `PROJECT-REFERENCE.md` برای مدل داده، فرمول‌ها و رفتار UI.
6. `REMEDIATION-ROADMAP.md` برای کارهای نیمه‌تمام.
7. اسناد تخصصی backup، تولید، فاکتور/چک، vendor، APK و emergency recovery.

روش اصلاحی پروژه عموماً به‌صورت checkpointهای کوچک انجام شده است: ابتدا قرارداد داده و رفتار در سند ثبت شده، سپس مدل و migration تغییر کرده، تست مدل اضافه یا اصلاح شده، بعد UI متصل شده و در پایان `pnpm check`، `pnpm build` و `git diff --check` اجرا شده‌اند. این روش برای حفظ سازگاری backup و جلوگیری از تغییر خاموش فرمول‌های مالی مناسب است و باید ادامه یابد.

## ۹. یافته‌های مهم و اولویت‌ها

### اولویت بالا

1. **تست رسمی در package scripts وجود ندارد.** Vitest نصب است اما `pnpm test` تعریف نشده و CI استاندارد برای test مشاهده نشد. باید script رسمی، coverage threshold و اجرای `check/test/build` در CI اضافه شود.
2. **تست UI/E2E وجود ندارد.** ثبت فاکتور چندواحدی، تولید، ثبت چک، restore و مسیرهای موبایل فقط از طریق مدل یا بررسی دستی پوشش دارند. فرم‌های حساس به Playwright یا ابزار مشابه نیاز دارند.
3. **تمرکز بیش از حد در `Home.tsx`.** تفکیک domain-specific pageها و hookهای mutation ریسک regression را کم می‌کند؛ اولویت با invoices، checks، production و backup است.
4. **قرارداد snapshot و ledger باید سخت‌تر شود.** مستندات خود پروژه هنوز پوشش کامل ویرایش/حذف و drill-down همهٔ eventها را باز می‌دانند. قبل از APK باید migration، reversal و بازسازی projection برای هر mutation کامل و تست شود.

### اولویت متوسط

1. **Prettier در ۲۳ فایل شکست خورد.** پیش از refactor بزرگ، format baseline ثبت و در CI enforce شود.
2. **Bundle اصلی حدود ۶۸۸KB minified است.** گزارش، تولید و backup باید lazy-load یا code-split شوند.
3. **هشدار pnpm دربارهٔ فیلد `pnpm` در package.json.** محیط نصب فعلی اعلام کرد `patchedDependencies` و `overrides` دیگر از این محل خوانده نمی‌شوند. در clone تازه باید مشخص شود patch وابستگی wouter و override nanoid عملاً از lockfile اعمال می‌شوند؛ بهتر است تنظیمات به `pnpm-workspace.yaml` منتقل و با CI clean install تأیید شوند.
4. **Routing واقعی وجود ندارد.** برای deep link، bookmark، back/forward مرورگر و گزارش‌پذیری بهتر، routeهای پایدار یا حداقل state قابل بازیابی پیشنهاد می‌شود.
5. **امنیت محلی، احراز هویت کاربر نیست.** hash محلی و PIN فقط قفل همان browser/device هستند؛ multi-user، tenant isolation و server authorization هنوز وجود ندارد و اسناد نیز این مرز را درست بیان کرده‌اند.

### اولویت پایین/محصولی

1. در جدول‌های عریض موبایل، نمای کارت و ستون‌های اولویت‌دار لازم است.
2. برای actionهای icon-only، label یا tooltip قابل دسترس باید کامل شود.
3. صفحه‌های گزارش باید drill-down قطعی به سند مادر و شناسهٔ event داشته باشند.
4. ادامهٔ برنامهٔ APK و customer portal نباید پیش از تثبیت migration، restore و ledger انجام شود.
