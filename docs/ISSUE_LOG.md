### ۲. ریشه‌یابی فنی خطا (Root Cause Analysis)

بررسی دقیق مخزن، تنظیمات گیت‌هاب، تاریخچهٔ اکشن‌ها و تحلیل اسکرین‌شات سه علت ریشه‌ای را آشکار کرد:

#### علت ۱: رفتار پیش‌فرض موتور Jekyll در حالت `Deploy from a branch`
- در تنظیمات مخزن گیت‌هاب (**Settings > Pages**)، گزینهٔ **Source** روی حالت پیش‌فرض `Deploy from a branch (Branch: main, /root)` تنظیم شده بود.
- در این حالت، گیت‌هاب فایل‌های سورس پروژهٔ Vite/React را بیلد نمی‌کند، بلکه کل پوشهٔ ریشه شاخهٔ `main` را به موتور سایت‌ساز Jekyll می‌سپارد. موتور Jekyll به صورت خودکار فایل `README.md` ریشه را تبدیل به یک صفحهٔ سادهٔ HTML کرده و تحویل مرورگر می‌داد.
- چون فایل اولیهٔ `README.md` مخزن شامل بنر و معرفی اولیه بود، همان متن در مرورگر کاربر نمایش داده شده بود.

#### علت ۲: خطای `ERESOLVE` در اولین اجرای GitHub Actions
- ورک‌فلو اولیهٔ `.github/workflows/deploy-pages.yml` که برای بیلد خودکار پوشهٔ `dist/public` ساخته شده بود، در اولین اجرا در مرحلهٔ `Install dependencies` با خطای شکست مواجه شد:
  ```text
  npm error code ERESOLVE
  npm error ERESOLVE could not resolve
  npm error Conflicting peer dependency: vite@5.4.21
  npm error from @builder.io/vite-plugin-jsx-loc@0.1.1
  ```
- چون پکیج `@builder.io/vite-plugin-jsx-loc` نیازمند وایت ۵ بود و پروژه با وایت ۷ اجرا می‌شود، دستور پیش‌فرض `npm install` در سرور اوبونتو متوقف شده بود و خروجی بیلد آماده نشده بود.

#### علت ۳: شرایط نصب PWA در موتور Chromium و مرورگر Microsoft Edge
- مرورگر Microsoft Edge برای اینکه آیکون نصب (Install App) را در نوار آدرس نشان دهد، معیارهای سخت‌گیرانه‌ای دارد:
  1. دارا بودن حداقل یک آیکون با ابعاد ۱۹۲x۱۹۲ و یک آیکون با ابعاد ۵۱۲x۵۱۲ در فرمت **PNG** (فایل‌های خالص SVG برای پرامپت خودکار اج کافی نیستند).
  2. تفکیک واضح `purpose: "any"` از `purpose: "maskable"` (آیکون ماسک‌بل باید دارای ۱۰ الی ۱۵ درصد حاشیه امن safe-zone باشد).
  3. وجود دکمهٔ تعاملی گوش‌به‌زنگ برای رویداد `beforeinstallprompt` درون رابط کاربری برنامه.
  4. تطابق آدرس‌های `scope` و `start_url` با زیرمسیر مخزن در GitHub Pages.

### ۴. جزئیات دقیق پیاده‌سازی و تغییرات کد (Implementation Details)

#### ۱. تصحیح ورک‌فلو گیت‌هاب (`/.github/workflows/deploy-pages.yml`)
- افزودن فلگ `--legacy-peer-deps` به مرحلهٔ نصب.
- قرار دادن انتشار دوگانه با اکشن `peaceiris/actions-gh-pages@v4` روی شاخهٔ `gh-pages`:
```yaml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: write
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 22
      - name: Install dependencies
        run: npm install --legacy-peer-deps
      - name: Build static site
        run: npm run build
        env:
          GITHUB_ACTIONS: "true"
      - name: Configure Pages
        uses: actions/configure-pages@v5
      - name: Upload Pages artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: dist/public
      - name: Deploy to gh-pages branch
        uses: peaceiris/actions-gh-pages@v4
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./dist/public
          force_orphan: true

  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    needs: build
    steps:
      - name: Deploy
        id: deployment
        uses: actions/deploy-pages@v4
```

### ۱. شرح درخواست و تذکر کاربر (User Request & Complaint)
کاربر با اعلام تذکر صریح پیرامون دستکاری ناخواسته در فرآیند تخصیص چک بر خلاف توافقات قبلی، موارد زیر را معین و مطالبه نمود:
1. **اصل دست‌نخوردن توافقات:** هیچ‌یک از محاسبات و اصولی که پیش‌تر با کاربر توافق شده نباید بدون اجازه و تأیید صریح دستکاری شود.
2. **اصلاح مبنای پله‌ها در تخصیص چک:** پله‌های سود/هزینه دیرکرد باید الزاماً بر اساس **فاصلهٔ تقویمی تاریخ فاکتور و تاریخ سررسید چک** محاسبه شوند، در حالی که در کد به اشتباه بر اساس تاریخ وصول محاسبه شده و در چک‌های نزد ما صفر می‌شد.
3. **قوانین قطعی FIFO:**
   - فاکتورها به ترتیب تاریخ صعودی (قدیمی‌ترین اول) و چک‌ها به ترتیب تاریخ سررسید صعودی (نزدیک‌ترین سررسید اول) مرتب شوند. با ورود چک جدید، این مرتب‌سازی مجدداً صورت گیرد.
   - چک با سررسید نزدیک‌تر به قدیمی‌ترین فاکتور باز تخصیص می‌یابد. اگر فاکتور تسویه شد و چک مانده داشت، چک شکسته شده و به فاکتور بعدی تخصیص می‌یابد. اگر مبلغ چک کمتر بود، چک بعدی ادامهٔ تسویه فاکتور را انجام می‌دهد.
   - هیچ فاکتوری بیشتر از ۱۰۰٪ تسویه نمی‌شود و تا فاکتور قدیمی‌تر تسویه نشده، فاکتور جدیدتر تخصیص نخواهد یافت.
   - کنترل اعشار (`FIFO_EPSILON`) حفظ شود تا مانع تسویه ۱۰۰٪ نشود.
4. **قابلیت جدید درخواستی (تخصیص اختصاصی چک به فاکتور خاص):**
   امکانی فراهم شود که اگر بنا به درخواست مشتری چک خاصی برای فاکتور خاصی در نظر گرفته شده باشد، آن چک مستقیماً به آن فاکتور تخصیص یابد و در صورتی که فاکتورهای قبلی آن مشتری هنوز تسویه نشده باشند، با چک‌های بعدی تسویه شوند.

این تغییر فاجعه‌بار باعث شده بود:

- **فاز ۲ (تسویه ترتیبی عمومی FIFO):**  
  سایر چک‌ها و ماندهٔ چک‌های فاز ۱، به ترتیب تاریخ سررسید (`dueDate`) به قدیمی‌ترین فاکتورهای باز مشتری (شامل فاکتورهای قدیمی‌تری که هدف‌گذاری نشده بودند) تخصیص می‌یابند. این تضمین می‌کند که فاکتور قبلی با چک بعدی تسویه شود.

### ۱. شرح کامل درخواست و سناریوی کاربر (User Request & Scenario)
کاربر اساس دقیق محاسبه تخصیص چک، دیرکرد پله‌ای، مانده فاکتور، تخصیص گروهی و قالب چاپ را در قالب فرمول گام‌به‌گام و مثال عددی تبیین کرد:

1. **فرمول و الگوریتم ریاضی گام‌به‌گام:**
   - تعداد روزهای مشمول دیرکرد: $y$ (بر مبنای پله‌ها و فاصله تقویمی فاکتور تا سررسید چک).
   - نرخ روزانه دیرکرد: $r = \frac{\text{monthlyRate}}{\text{dayBasis}}$ (مثلاً $\frac{6\%}{30} = 0.2\%$).
   - درصد کل روزهای دیرکرد: $Z = r \times y$ (برای ۵۴ روز: $54 \times 0.2\% = 10.8\%$).
   - اگر مبلغ فاکتور (یا مانده پایه) برابر $P$ باشد:
     - دیرکرد کل فاکتور تا سررسید: $\text{lateFee} = P \times Z = P \times r \times y$
     - ارزش کل فاکتور بعلاوه دیرکرد کل در موعد سررسید: $K = P \times Z + P = P \times (1 + Z)$
   - اگر مبلغ چک تخصیص‌یافته برابر $X$ باشد:
     - باقیمانده فاکتور بعلاوه دیرکرد در موعد سررسید چک: $L = K - X$
     - باقیمانده خالص فاکتور به ارزش پایه: $G = \frac{L}{1 + Z}$
     - اصل تسویه شده از فاکتور با این چک: $P - G$
     - سهم دیرکرد پرداخت شده با این چک: $X - (P - G)$
     - باقیمانده چک: $\max(0, X - K)$

2. **مثال عددی کاربر:**
   - فاکتور: $P = ۲۰۰{,}۰۰۰{,}۰۰۰$ تومان
   - چک تخصیص‌داده‌شده: $X = ۱۰۰{,}۰۰۰{,}۰۰۰$ تومان
   - اختلاف تعداد روز: ۵۴ روز ($y = 54$)
   - مشمول پله ماهیانه ۶٪ یعنی روزی ۰.۲٪ ($r = 0.002$)
   - درصد کل دیرکرد: $Z = 54 \times 0.2\% = 10.8\%$
   - دیرکرد کل فاکتور: $200{,}000{,}000 \times 10.8\% = 21{,}600{,}000$ تومان
   - کل فاکتور در ۵۴ روز دیرکرد: $K = 200{,}000{,}000 \times 1.108 = 221{,}600{,}000$ تومان
   - کسر مبلغ چک از فاکتور بعلاوه دیرکرد: $L = 221{,}600{,}000 - 100{,}000{,}000 = 121{,}600{,}000$ تومان
   - اصل باقیمانده خالص فاکتور: $G = \frac{121{,}600{,}000}{1.108} = 109{,}747{,}292.42$ تومان
   - باقیمانده چک: ۰ تومان
   - اصل تسویه شده: $200{,}000{,}000 - 109{,}747{,}292.42 = 90{,}252{,}707.58$ تومان
   - دیرکرد پرداخت شده با چک: $100{,}000{,}000 - 90{,}252{,}707.58 = 9{,}747{,}292.42$ تومان

3. **مثال فاکتور و چندچک متوالی:**
   - فاکتور A: ۳۶۰ عدد قطعه به قیمت ۵۶۰٬۰۰۰ تومان = ۲۰۱٬۶۰۰٬۰۰۰ تومان، ثبت‌شده در تاریخ ۱۴۰۵/۰۶/۰۷.
   - چک ۱: ۲۰۰٬۰۰۰٬۰۰۰ تومان با سررسید ۱۴۰۵/۰۷/۳۰ (۵۴ روز دیرکرد).
   - کل فاکتور در روز ۵۴: $۲۰۱{,}۶۰۰{,}۰۰۰ \times ۱.۱۰۸ = ۲۲۳{,}۳۷۲{,}۸۰۰$ تومان.
   - تسویه با چک ۱: $۲۲۳{,}۳۷۲{,}۸۰۰ - ۲۰۰{,}۰۰۰{,}۰۰۰ = ۲۳{,}۳۷۲{,}۸۰۰$ تومان ($L$).
   - بازگشت به ارزش روز صدور: $G = ۲۳{,}۳۷۲{,}۸۰۰ \div ۱.۱۰۸ = ۲۱{,}۰۹۴{,}۵۸۴.۸۴$ تومان مانده پایه فاکتور.
   - چک ۲: ۵۰٬۰۰۰٬۰۰۰ تومان با دیرکرد ۸۰ روز ($۸۰ \times ۰.۲\% = ۱۶\%$).
   - مانده فاکتور در روز ۸۰: $۲۱{,}۰۹۴{,}۵۸۴.۸۴ \times ۱.۱۶ = ۲۴{,}۴۶۹{,}۷۱۸.۴۱$ تومان ($K_2$).
   - تسویه با چک ۲: $۵۰{,}۰۰۰{,}۰۰۰ - ۲۴{,}۴۶۹{,}۷۱۸.۴۱ = ۲۵{,}۵۳۰{,}۲۸۱.۵۹$ تومان مانده چک ۲ جهت انتقال به فاکتورهای بعدی، و مانده فاکتور صفر.
2. **قوانین حاکم:**
   - **قانون ۱:** هیچ فاکتوری بیشتر از ۱۰۰٪ تسویه نمی‌شود.
   - **قانون ۲:** تا فاکتور قدیمی‌تر تسویه نشده، چکی به فاکتور بعدی تخصیص نمی‌یابد (مگر در تخصیص خاص یا گروهی).
3. **تخصیص گروهی (Group Allocation):**
   - قابلیت تخصیص دسته‌ای از چک‌ها (مانند $z_1, z_2, z_3, z_4$) به دسته‌ای از فاکتورها (مانند ۱۰۱۰، ۱۰۱۱، ۱۰۱۲) به صورت دستی. مابقی چک‌ها و فاکتورها طبق روال عادی تسویه شوند.

### ۲. ریشه‌یابی و تطبیق الگوریتم محاسباتی (Technical Implementation)

#### ۲.۱. فرمول محاسبه دیرکرد و پله‌ها در `calculateLateProfit`
- پله‌های شرط پرداخت بر اساس `maxDays` صعودی مرتب می‌شوند.
- در صورتی که پله با نرخ صفر تعریف شده باشد (`hasZeroRateTier = true`)، با عبور روزها از سقف آن، کل روزهای تقویمی مشمول دیرکرد می‌شوند (`overdueDays = days`).
- در صورت وجود `graceDays` روی قاعده بدون پله صفر، تنفس کسر می‌شود (`Math.max(0, days - graceDays)`).
- محاسبه دقیق مبلغ سررسید (`settled`)، سود دیرکرد (`profit`)، مانده پس از کسر چک (`remaining`) و تبدیل معکوس به ارزش پایه روز صدور فاکتور (`remainingBase`):
  $$\text{remainingBase} = \frac{\text{remaining}}{1 + \frac{\text{rate} \times \text{overdueDays}}{\text{dayBasis}}}$$

#### ۲.۲. الگوریتم سه‌فازی تسویه در `settleChecksFIFO`
1. **فاز ۱ (تخصیص گروهی):** اجرای متوالی تسویه بین چک‌ها و فاکتورهای هر گروه تعریف‌شده در `checkGroupAllocations`.
2. **فاز ۲ (تخصیص اختصاصی):** اجرای تسویه چک‌های دارای `targetInvoiceId`.
3. **فاز ۳ (تسویه ترتیبی خودکار FIFO):** تسویه باقیمانده‌ها بر اساس تقدم تاریخی فاکتورها و سررسید چک‌ها.
