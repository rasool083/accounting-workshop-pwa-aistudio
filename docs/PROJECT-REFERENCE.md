# مستند مرجع پروژه حسابداری کارگاه

**آخرین به‌روزرسانی:** ۱۴۰۵/۰۶/۲۸

## هدف پروژه

این پروژه نسخهٔ مستقل، فارسی، راست‌به‌چپ و local-first حسابداری کارگاه است. هدف آن جایگزین‌کردن فایل‌های پراکندهٔ Excel و Google Sheets با یک دفتر عملیاتی قابل استفاده در موبایل و دسکتاپ است. داده‌ها ابتدا در حافظهٔ محلی مرورگر ذخیره می‌شوند و امکان پشتیبان‌گیری JSON و بازیابی نسخهٔ معتبر دارند. برنامه به‌صورت PWA قابل نصب است و نسخهٔ منتشرشده از GitHub Pages در دسترس قرار می‌گیرد.

Repository اصلی پروژه `rasool083/accounting-workshop-pwa` است. Repository اولیهٔ `rasool083/Accounting-` فقط برای مطالعه و تحلیل استفاده شده و در آن تغییری ایجاد نمی‌شود.

## اصول طراحی و روش کار

هستهٔ داده در `client/src/lib/accounting.ts` قرار دارد و رابط کاربر در `client/src/pages/Home.tsx` پیاده‌سازی شده است. هر تغییر باید ابتدا در مدل داده، سپس در منطق محاسبه و در پایان در رابط کاربر اعمال شود. ذخیره‌سازی باید از طریق `saveState` انجام شود تا نسخه، زمان تغییر و رویداد حسابرسی ثبت شود.

تغییرات destructive مانند حذف فاکتور، حذف چک یا اصلاح موجودی باید با کنترل کاربر انجام شوند و در صورت امکان رویداد حسابرسی تولید کنند. فاکتور تسویه‌شده نباید بدون سند اصلاحی تغییر کند. ویرایش فاکتور تسویه‌نشده باید ابتدا اثر گردش قبلی را از موجودی برگرداند و سپس اثر گردش جدید را اعمال کند.

هر مرحله باید با `pnpm check` و `pnpm build` کنترل شود. پس از موفقیت، preview تعاملی بررسی و checkpoint پروژه ثبت می‌شود. برای انتشار GitHub Pages، ابتدا باید Pages در تنظیمات repository فعال باشد و سپس workflow `deploy-pages.yml` اجرا شود.

## روش درست محاسبه فاکتور و چک

مبلغ فاکتور با تبدیل مقدار واردشده به واحد اول و ضرب آن در قیمت واحد اول به دست می‌آید. واحد انتخاب‌شده در فاکتور می‌تواند واحد اول یا واحد دوم کالا باشد، اما تاریخچهٔ قیمت و قیمت واردشده همیشه مربوط به واحد اول است. بنابراین مقدار نمایش‌داده‌شده برای کاربر «مقدار واردشده» است و مقدار مبنای محاسبه «معادل واحد اول» خواهد بود.

برای نمونه، اگر هر کارتن شامل ۳۶ عدد باشد و قیمت واحد اول هر عدد ۳۰۰٬۰۰۰ تومان باشد، ثبت ۱۰ کارتن برابر با ۳۶۰ عدد و مبلغ ۱۰۸٬۰۰۰٬۰۰۰ تومان است. اگر کاربر ۱۰ عدد بفروشد، مبلغ ۳٬۰۰۰٬۰۰۰ تومان خواهد بود. اگر کمتر از یک کارتن فروخته شود، کاربر می‌تواند واحد را به عدد تغییر دهد و تبدیل واحد به‌صورت دقیق اعمال می‌شود. عنوان قیمت در رابط کاربری باید «قیمت پایه» یا «قیمت واحد اول» باشد تا با قیمت یک کارتن اشتباه نشود.

در بستن ماه، فاکتورهای فروش هر مشتری بر اساس تاریخ مرتب می‌شوند. چک‌ها نیز بر اساس تاریخ سررسید مرتب می‌شوند و هر چک به قدیمی‌ترین فاکتور باز تخصیص می‌یابد. اگر مبلغ چک از ماندهٔ فاکتور بیشتر باشد، فقط مقدار لازم برای همان فاکتور مصرف می‌شود و مابقی چک به فاکتور بعدی منتقل می‌گردد.

فرمول ارزش فاکتور در تاریخ سررسید چک چنین است:

```text
روزهای مشمول = حداکثر(۰، فاصلهٔ تاریخ فاکتور تا سررسید − روزهای تنفس)
نرخ مؤثر = نرخ پله × روزهای مشمول ÷ مبنای روزشمار
سود دیرکرد = اصل باقی‌مانده × نرخ مؤثر
ارزش سررسید = اصل باقی‌مانده + سود دیرکرد
مانده پس از چک = ارزش سررسید − مبلغ تخصیص‌یافتهٔ چک
اصل باقیمانده = مانده پس از چک ÷ (۱ + نرخ مؤثر)
```

مثال کنترل‌شده: برای فاکتور ۱۰۰٬۰۰۰٬۰۰۰ تومانی و چک اول ۸۰٬۰۰۰٬۰۰۰ تومانی با اختلاف ۴۵ روز، نرخ مؤثر ۹٪ است. اصل پوشش‌داده‌شده `۸۰٬۰۰۰٬۰۰۰ ÷ ۱٫۰۹` و ماندهٔ اصل فاکتور `۲۶٬۶۰۵٬۵۰۴٫۵۹` تومان می‌شود. اگر چک دوم ۵۰٬۰۰۰٬۰۰۰ تومان با اختلاف ۶۰ روز باشد، ارزش سررسید ماندهٔ فاکتور با نرخ مؤثر ۱۲٪ از مبلغ چک کمتر است؛ بنابراین فاکتور صفر و ماندهٔ چک `۲۰٬۲۰۱٬۸۳۴٫۸۶` تومان خواهد بود. مانده‌ها در آکاردئون فاکتور و آکاردئون چک باید بعد از همان ردیف تخصیص نمایش داده شوند، نه ماندهٔ نهایی در همهٔ ردیف‌ها.

## چرخهٔ چک

وضعیت‌های پشتیبانی‌شده عبارت‌اند از «نزد ما»، «وصول شده»، «برگشتی»، «عودت داده شده»، «جایگزین شده» و «باطل». چک‌های نزد ما سفید، چک‌های وصول‌شده سبز، چک‌های برگشتی، عودت‌شده و باطل قرمز، چک اصلی جایگزین‌شده زرد و چک جایگزین نارنجی طراحی می‌شوند.

برای چک وصول‌شده، حساب بانکی انتخاب می‌شود. هنگام ثبت، مبلغ چک به ماندهٔ حساب بانکی اضافه و یک تراکنش دریافت ثبت می‌شود. چک جایگزین نباید دوباره فاکتور را تسویه کند؛ چک اصلی باید به فاکتور تخصیص یافته باشد و چک جایگزین فقط رابطهٔ جایگزینی و تاریخ جدید را نگهداری کند. تفاوت سود بین سررسید چک اصلی و جایگزین در مرحلهٔ بعد باید به‌صورت اطلاع‌رسانی جداگانه نمایش داده شود، نه به‌عنوان تسویهٔ مجدد.

## پشتیبان‌گیری و بازیابی

پشتیبان JSON باید شامل کل `AppState`، نسخهٔ schema، زمان ایجاد خروجی و داده‌های حسابرسی باشد. بازیابی باید ابتدا JSON را parse کند، ساختار را normalize کند و سپس آن را در localStorage ذخیره کند. قبل از بازیابی اطلاعات مهم، کاربر باید یک خروجی پشتیبان از وضعیت فعلی بگیرد.

## مشکلات شناسایی‌شده و راه‌حل‌ها

در repository اولیه، منطق‌های حسابداری میان فایل‌ها پراکنده بود و محدوده‌های ثابت Excel برای افزایش تعداد رکوردها مناسب نبود. راه‌حل، انتقال مدل به آرایه‌های نسخه‌دار و ایجاد یک هستهٔ محاسباتی واحد بود.

در نسخه‌های اولیه، چک به فاکتور به‌صورت مستقیم وابسته بود. این با فرآیند واقعی کارگاه سازگار نبود، زیرا چک مستقل از فاکتور دریافت می‌شود. راه‌حل، تخصیص FIFO بر اساس مشتری و تاریخ فاکتور است.

در محاسبهٔ قبلی، سود روی مبلغ چک محاسبه می‌شد. این باعث می‌شد ارزش بدهی واقعی فاکتور به‌درستی محاسبه نشود. راه‌حل فعلی سود را روی اصل باقی‌ماندهٔ فاکتور محاسبه می‌کند و پس از کسر چک، اصل باقی‌مانده را از ارزش روز برگشت می‌دهد.

در GitHub Pages، repository ابتدا خصوصی بود و GitHub در سطح طرح و مجوز اتصال اجازهٔ ایجاد Pages نمی‌داد. پس از تأیید کاربر، repository عمومی شد. سپس تنظیم Source روی GitHub Actions در GitHub ذخیره شد. گزینهٔ `enablement: true` از workflow حذف شد، زیرا اتصال API مجوز ایجاد Pages را نداشت و باید از Pages از پیش فعال‌شده استفاده می‌کرد. پس از آن workflow با موفقیت اجرا شد.

## وضعیت فعلی و کارهای باقی‌مانده

نسخهٔ فعلی شامل فاکتور چندردیفی، واحد دوم و نسبت تبدیل، انبارهای متعدد، کاردکس، تاریخچه قیمت هدفمند، شرایط پرداخت و پله‌های سود، چک‌های دارای وضعیت، بستن ماه مشتری‌محور، FIFO، حذف رکوردهای اصلی، اصلاح موجودی، چاپ و خروجی جزئیات بستن ماه است.

موارد مهم باقی‌مانده عبارت‌اند از ویرایش مستقل همهٔ موجودیت‌ها با آیکون مداد، تکمیل زنجیرهٔ چندچک جایگزین، نمایش سود اطلاع‌رسانی چک جایگزین، گزارش PDF با سربرگ رسمی، همگام‌سازی واقعی Google Drive و تست‌های واحد برای سناریوهای مالی.

## روش ثبت مستندات آینده

از این مرحله، هر تغییر مهم باید در انتهای همین فایل در بخش «ثبت تغییرات» و با تاریخ، هدف، فایل‌های تغییرکرده، نتیجهٔ آزمون و محدودیت‌های باقی‌مانده ثبت شود. جزئیات کوتاه commit نیز باید در `docs/CHANGELOG.md` اضافه شود. هیچ محاسبهٔ مالی بدون مثال عددی و توضیح واحد پولی وارد پروژه نشود.

### ۱۴۰۵/۰۶/۲۶ — کنترل سطرها و عملیات CRUD

برای سطرهای ایجادشده در فاکتورها، عملیات مالی، طرف حساب‌ها، کالاها، انبارها، تاریخچه قیمت، شرایط پرداخت و چک‌ها آیکون مداد و سطل زباله اضافه شد. آیکون مداد، ویرایش واقعی مقدار مرتبط با همان رکورد را انجام می‌دهد و آیکون سطل زباله پس از تأیید کاربر رکورد را از مجموعهٔ همان صفحه حذف می‌کند. فاکتورهای دارای پرداخت همچنان از ویرایش و حذف مستقیم محافظت می‌شوند تا مانده و تخصیص چک دچار مغایرت نشود. جدول‌های بستن ماه و کاردکس، دادهٔ محاسباتی هستند و رکورد مستقل قابل حذف ندارند؛ منبع آن‌ها از صفحات فاکتور و چک کنترل می‌شود.

### ۱۴۰۵/۰۶/۲۶ — بازطراحی کامل چرخه چک و ویرایش اطلاعات

فرم ویرایش طرف حساب اکنون تمام اطلاعات ثبت‌شده شامل نام، نقش‌های چندگانه، تلفن و شرایط پرداخت پیش‌فرض را باز می‌کند. فرم ویرایش چک نیز تمام اطلاعات چک را باز می‌کند.

در دفتر چک، ستون وضعیت شامل «نزد ما»، «وصول شده»، «برگشتی»، «عودت»، «جایگزین»، «باطل» و «خرج شده» است. ستون بعدی به وضعیت وابسته است: برای سه وضعیت مرجع، حساب بانک، صندوق یا شریک انتخاب می‌شود؛ برای عودت یا خرج‌شدن، شخص یا تأمین‌کننده انتخاب می‌شود. وصول چک ابتدا اثر وصول قبلی را از حساب قبلی برمی‌گرداند و سپس مبلغ را به حساب مرجع جدید اضافه می‌کند. چک خرج‌شده توضیح مستقل دارد.

وضعیت جایگزین، فرم افزودن چند چک را باز می‌کند. هر خط با قالب `شماره:مبلغ` به یک چک جایگزین با رابطهٔ `replacementOf` تبدیل می‌شود. چک اصلی زرد، چک وصول‌شده سبز، چک برگشتی/عودت/باطل قرمز، چک خرج‌شده آبی و چک جایگزین نارنجی نمایش داده می‌شود.

### ۱۴۰۵/۰۶/۲۶ — فیلتر و تاریخچهٔ چک

دفتر چک اکنون بر اساس وضعیت و حساب بانکی فیلتر می‌شود و تعداد رکوردهای قابل مشاهده در کنار تعداد کل نمایش داده می‌شود. برای هر چک دکمهٔ تاریخچه اضافه شده است. ایجاد چک، ویرایش کامل و تغییر وضعیت در رویدادهای حسابرسی ثبت می‌شود و تاریخچه با زمان، نوع رویداد و توضیح قابل مشاهده است.

### ۱۴۰۵/۰۶/۲۶ — گزارش دفتر چک و فیلتر بازهٔ زمانی

دفتر چک اکنون بر اساس تاریخ دریافت و تاریخ سررسید، با بازهٔ از و تا، فیلتر می‌شود. خروجی CSV فقط رکوردهای فیلترشده را شامل می‌کند و ستون‌های شماره، طرف حساب، تاریخ‌ها، مبلغ، وضعیت، مرجع بانکی/شخصی و توضیحات را دارد. دکمهٔ چاپ گزارش برای چاپ دفتر چک و ذخیرهٔ آن به PDF اضافه شد.

### ویرایش کامل رکوردها و چک جایگزین

آیکون مداد در کالا، انبار، تاریخچه قیمت و شرایط پرداخت اکنون همان فرم کامل ثبت رکورد را با مقادیر موجود باز می‌کند. چک جایگزین یک رکورد مستقل است که با `replacementOf` به چک اصلی اشاره می‌کند؛ هر بار دکمهٔ «افزودن چک جایگزین» فرم کامل جدیدی باز می‌کند. چک اصلی حذف نمی‌شود و پس از وصول همهٔ جایگزین‌های متصل، وضعیت آن به «وصول شده» و رنگ سطر آن سبز می‌شود. حذف چک اصلی دارای جایگزین مسدود است، اما جایگزین‌ها مستقل و قابل ویرایش/حذف هستند.

### ۱۴۰۵/۰۶/۲۶ — adapter امن Google Drive

فایل `client/src/lib/googleDrive.ts` یک adapter مستقل برای فهرست‌کردن، بارگذاری و بازیابی فایل‌های JSON پشتیبان روی Google Drive اضافه می‌کند. OAuth access token فقط از host/connector به‌صورت کوتاه‌عمر وارد adapter می‌شود و در `localStorage`، `AppState` یا فایل پشتیبان ذخیره نمی‌شود. جست‌وجوی فایل‌ها به نام‌های `accounting-workshop-backup` محدود شده و امکان تعیین پوشهٔ مقصد وجود دارد.

در صفحهٔ پشتیبان، خروجی JSON شامل کل `AppState` با شماره schema و زمان خروجی‌گیری ساخته می‌شود و بازیابی از فایل پس از parse و `normalizeState` انجام می‌گیرد. حذف همهٔ اطلاعات فقط پس از واردکردن دقیق عبارت «حذف کامل» فعال می‌شود. قبل از اجرای آن، خروجی JSON به‌طور خودکار دانلود می‌شود؛ سپس داده‌های عملیاتی شامل طرف حساب‌ها، کالاها، فاکتورها، عملیات، چک‌ها و تاریخچه قیمت حذف می‌شوند. تنظیمات پایه، انبارهای پیش‌فرض، حساب‌های پایه و قاعدهٔ پرداخت نقدی حفظ می‌شوند تا برنامه پس از پاک‌سازی قابل استفاده بماند. رویداد `CLEAR_DATA` برای حسابرسی ثبت می‌شود.

### فهرست و بازیابی نسخه‌های Google Drive

صفحهٔ پشتیبان یک نسخهٔ تأییدشدهٔ Drive را با نام و حجم نشان می‌دهد. بازیابی نسخهٔ Drive فقط پس از تأیید صریح کاربر انجام می‌شود؛ adapter با access token کوتاه‌عمر host فایل JSON را دریافت می‌کند، آن را از مسیر `importPayload` عبور می‌دهد و با رویداد `RESTORE_DRIVE` در حسابرسی ذخیره می‌کند. token در localStorage، AppState یا فایل JSON قرار نمی‌گیرد. در صورت نبود token مرورگر، رابط پیام روشن نمایش می‌دهد و لینک بازکردن پوشهٔ اختصاصی در اختیار کاربر است.

### بارگذاری مستقیم پشتیبان در Drive

تابع `handleDriveUpload` خروجی `exportPayload(state)` را با نام زمان‌دار به `PROJECT_BACKUPS_FOLDER_ID` ارسال می‌کند. adapter از upload multipart رسمی Drive استفاده می‌کند و access token فقط در زمان اجرای درخواست در حافظه قرار دارد. پس از پاسخ موفق، فایل جدید به فهرست رابط اضافه می‌شود تا بلافاصله قابل بازیابی باشد. نبود token باعث fallback به دانلود بکاپ محلی می‌شود و برنامه بدون اتصال ابری نیز کامل کار می‌کند.

### تازه‌سازی فهرست نسخه‌های Drive

وقتی `activePage` برابر `backup` می‌شود، برنامه با adapter و token موقت host فهرست فایل‌های JSON را از پوشهٔ اختصاصی Drive می‌خواند. دکمهٔ دستی نیز همان مسیر را اجرا می‌کند و تا پایان درخواست غیرفعال است. فهرست در React state نگهداری می‌شود و فقط metadata فایل‌ها را شامل می‌شود؛ محتوای پشتیبان تا زمان انتخاب بازیابی دریافت نمی‌شود.

### قواعد قطعی تخصیص چک و سود دیرکرد

موتور `settleChecksFIFO` ابتدا چک‌های معتبر هر طرف حساب را بر اساس `dueDate`، سپس تاریخ دریافت و شماره چک مرتب می‌کند؛ بنابراین ثبت دیرهنگام یک چک با سررسید قدیمی‌تر، ترتیب محاسبه را تغییر می‌دهد. فاکتورهای فروش نیز بر اساس تاریخ و شماره مرتب می‌شوند. هر چک فقط به قدیمی‌ترین فاکتور دارای مانده تخصیص می‌یابد و تا زمان تسویهٔ کامل آن فاکتور، به فاکتور بعدی عبور نمی‌کند.

برای هر تخصیص، ابتدا ضریب سود بر اساس بستهٔ شرایط پرداخت و اختلاف تاریخ فاکتور تا سررسید چک به دست می‌آید:

`ضریب = نرخ پله × روزهای مشمول ÷ مبنای روزشمار`

`ارزش تسویه فاکتور = اصل باقی‌مانده × (۱ + ضریب)`

اگر مبلغ باقی‌ماندهٔ چک کمتر از ارزش تسویه باشد، اصل تخصیص‌یافته برابر `مبلغ چک ÷ (۱ + ضریب)` است و کل چک به همان فاکتور می‌رسد. اگر چک از ارزش تسویه بیشتر باشد، فاکتور حداکثر تا ۱۰۰٪ اصل خود تسویه می‌شود و باقی‌ماندهٔ چک به فاکتور بعدی منتقل می‌گردد. در نتیجه `paidAmount` هیچ‌گاه از مبلغ اصل فاکتور بیشتر نمی‌شود. هر تخصیص علاوه بر مبلغ چک، اصل، سود و تعداد روز را در `CheckAllocation` ثبت می‌کند.

در سناریوی نمونهٔ ۱۰۰٬۰۰۰٬۰۰۰ تومانی با نرخ ۶٪ ماهانه، چک ۸۰٬۰۰۰٬۰۰۰ تومانی پس از ۴۵ روز با ضریب ۹٪، مبلغ اصل ۷۳٬۳۹۴٬۴۹۵٫۴۱ و سود ۶٬۶۰۵٬۵۰۴٫۵۹ را پوشش می‌دهد و اصل باقی‌مانده ۲۶٬۶۰۵٬۵۰۴٫۵۹ است. از چک ۵۰٬۰۰۰٬۰۰۰ تومانی بعدی، مبلغ ۲۹٬۷۹۸٬۱۶۵٫۱۴ برای تکمیل ارزش فاکتور اول مصرف و مبلغ ۲۰٬۲۰۱٬۸۳۴٫۸۶ به فاکتور بعدی منتقل می‌شود.

### ریز تخصیص و بازسازی FIFO

دفتر چک با اجرای `settleChecksFIFO(state.checks, state.invoices, state.paymentRules)` ریز تخصیص هر چک را نمایش می‌دهد: شماره فاکتور، اصل، سود و روزهای مشمول. دکمهٔ «محاسبه مجدد تخصیص‌ها» برای هر طرف حساب `applyCheckFIFO` را اجرا می‌کند؛ این تابع تخصیص‌های قبلی همان طرف را پاک‌سازی منطقی کرده و از روی تمام چک‌های معتبر، با ترتیب سررسید، مبلغ `paidAmount`، وضعیت فاکتور و `CheckAllocation`ها را دوباره می‌سازد.

تابع مشترک `suggestNextNumber` شماره‌های موجود را بررسی کرده و یک واحد به بزرگ‌ترین بخش عددی می‌افزاید. این راهبرد برای فاکتورها، چک‌ها، طرف حساب‌ها و کالاها به‌کار می‌رود. شماره هنگام باز شدن فرم پیشنهاد می‌شود، اما در input باقی می‌ماند تا کاربر بتواند آن را دستی تغییر دهد. کد طرف حساب با قالب `P-###` و کد کالا با قالب سه‌رقمی پیشنهاد می‌شود. ورودی‌های کد و شماره `inputMode="numeric"` دارند تا ورود در موبایل سریع‌تر باشد.

### ۱۴۰۵/۰۶/۲۷ — شماره‌گذاری گروهی، قیمت‌گذاری فاکتور و تخفیف

شماره‌گذاری فاکتور و چک با طرف حساب انتخاب‌شده گروه‌بندی می‌شود. سیستم آخرین بخش عددی سوابق همان طرف حساب را پیدا می‌کند و پیشوند موجود را حفظ می‌کند؛ بنابراین سوابق `M1005` و `T1003` به‌ترتیب پیشنهادهای `M1006` و `T1004` می‌سازند. در نبود سابقهٔ اختصاصی، شمارهٔ عمومی یا کد طرف حساب مبنا قرار می‌گیرد. مقدار پیشنهادی همیشه در input قابل اصلاح دستی است.

در فاکتور، قیمت پیشنهادی از جدیدترین تاریخچهٔ قیمت معتبر تا تاریخ فاکتور انتخاب می‌شود. قیمت عمومی برای همه و قیمت اختصاصی فقط برای طرف حساب‌های مشخص قابل استفاده است. انتخاب کالا، مشتری یا واحد دوباره این جست‌وجو را انجام می‌دهد. اگر واحد دوم انتخاب شود، مبلغ ردیف و مقدار پایهٔ انبار با نسبت تبدیل محاسبه می‌شود:

```text
مبلغ ردیف = مقدار واحد انتخابی × قیمت واحد × نسبت تبدیل واحد دوم به پایه
مقدار پایهٔ انبار = مقدار واحد انتخابی × نسبت تبدیل
مبلغ نهایی فاکتور = حداکثر(۰، جمع مبلغ ردیف‌ها − تخفیف مبلغی)
```

تخفیف در سطح فاکتور ذخیره می‌شود و در جزئیات فاکتور همراه با جمع اقلام و مبلغ نهایی نمایش داده می‌شود. پنجرهٔ ثبت فاکتور و چک ثابت و دارای اسکرول داخلی است تا مستقل از موقعیت فعلی صفحه در viewport باز شود.

### ۱۴۰۵/۰۶/۲۸ — قرارداد پایدار بکاپ

بکاپ با قالب `accounting-workshop-backup` و `backupFormatVersion` مستقل از نسخهٔ رابط ذخیره می‌شود. `data` شامل state کامل و نرمال‌شده است و `collections` تعداد رکوردهای طرف حساب، کالا، انبار، تاریخچه قیمت، شرایط پرداخت، فاکتور، عملیات، چک، حساب بانکی و حسابرسی را ثبت می‌کند. بازیابی ابتدا نسخهٔ قالب و schema را بررسی می‌کند، سپس migration و `normalizeState` را اجرا می‌کند. در نتیجه تغییرات آیندهٔ optional fields و ساختارهای جدید می‌توانند بدون از دست رفتن اطلاعات قدیمی افزوده شوند؛ فایل نسخهٔ جدیدتر از برنامهٔ فعلی جایگزین نمی‌شود.

### ۱۴۰۵/۰۶/۲۸ — ساختار تولید و بسته‌های تولید

مدل تولید شامل `ProductionFormula` برای نام فرمول، محصول خروجی، مقدار خروجی، مواد و هزینه‌های سربار است و `ProductionRecord` نتیجهٔ هر بچ تولید را با بهای مواد، سربار، کل و بهای واحد ذخیره می‌کند. هر ماده با مقدار و واحد ثبت می‌شود و اگر واحد دوم کالا انتخاب شود، مقدار پایه با `conversionRate` محاسبه می‌گردد:

```text
هزینه ماده = مقدار مصرف × نسبت تبدیل به واحد پایه × قیمت واحد پایه
هزینه کل تولید = جمع هزینه مواد + جمع هزینه سربار
بهای هر واحد = هزینه کل تولید ÷ مقدار خروجی
```

در تولید بستهٔ نیمه‌آماده، محصول خروجی به دستهٔ «بسته تولید» تغییر می‌کند و به انبار مواد اولیه منتقل می‌شود. بنابراین بستهٔ تولید بعدی در فهرست مواد اولیه فرمول‌های اصلی ظاهر می‌شود. موجودی ناکافی مادهٔ اولیه مانع ثبت عملیات می‌شود.

### ۱۴۰۵/۰۶/۲۹ — بازیابی بین دستگاهی و فیلتر اقلام

اتصال مستقیم Drive فقط زمانی کار می‌کند که میزبان مرورگر توکن OAuth موقت را تزریق کرده باشد؛ این توکن امنیتاً در localStorage، state یا فایل backup قرار نمی‌گیرد. در دستگاه جدید، روش قابل اتکا این است: پوشهٔ پشتیبان Drive باز شود، فایل JSON دانلود شود، در صفحهٔ پشتیبان کادر «بازیابی دستی» باز شود، متن فایل Paste و پس از اعتبارسنجی جایگزین شود. این روش به مجوز برنامه در دستگاه قبلی وابسته نیست.

فهرست اقلام فرم فاکتور بر اساس نوع سند محدود می‌شود: فروش از انبارهای دارای «محصول» یا «بازرگانی» و خرید از انبار دارای «مواد» می‌خواند. کالاهای بدون اتصال انبار همچنان برای سازگاری با داده‌های قدیمی قابل انتخاب‌اند.

### ۱۴۰۵/۰۶/۲۹ — استاندارد عملیات و سازمان‌دهی انبار

عملیات ردیف‌ها با selectorهای عنوان‌محور CSS یکپارچه شده است: دکمه‌های دارای عنوان ویرایش سبز و دکمه‌های دارای عنوان حذف قرمز هستند و اندازه ثابت ۲۹ پیکسل دارند تا در همه صفحات کنار هم بمانند. فاکتورهای تسویه‌شده قابل ویرایش و حذف‌اند؛ حذف فاکتور قبل از ذخیره، اثر گردش کالا را به موجودی برمی‌گرداند.

دفتر چک و دفتر فاکتور در جزئیات تخصیص، مبلغ تخصیص، اصل، سود و روزهای اختلاف را نمایش می‌دهند. صفحه انبار با warehouseFilter، کالاها را براساس شناسه انبار، بدون تغییر ساختار داده قبلی، در تب‌های جداگانه نمایش می‌دهد.

### ۱۴۰۵/۰۶/۲۹ — مبنای روزشمار تقویم شمسی

وقتی `settings.dayBasis` برابر «شمسی» باشد، مخرج سود روزشمار از ماه تاریخ فاکتور تعیین می‌شود: ۳۱ برای فروردین تا شهریور، ۳۰ برای مهر تا بهمن و ۲۹/۳۰ برای اسفند با تشخیص سال کبیسهٔ چرخهٔ ۳۳ ساله. این مقدار به موتور `settleChecksFIFO` و محاسبهٔ بستن ماه منتقل می‌شود. مقدار عددی همچنان به‌عنوان حالت ثابت برای داده‌های قدیمی پشتیبانی می‌شود.

فهرست واحدهای استاندارد در `settings.units` قرار دارد و صفحه تنظیمات آن را مدیریت می‌کند. واحد حذف نمی‌شود اگر آخرین واحد باشد تا فرم‌های کالا همیشه واحد معتبر داشته باشند؛ داده‌های واحد داخل export/import نیز نگهداری می‌شود.

### ۱۴۰۵/۰۶/۲۹ — مرجع واحدهای کالا

منبع واحدها `state.settings.units` است. فرم کالا، تاریخچه قیمت، ردیف آزاد فاکتور و تولید از این فهرست استفاده می‌کنند. `normalizeState` واحدهای `product.unit` و `product.unit2` را با فهرست تنظیمات ادغام می‌کند؛ بنابراین مهاجرت داده‌های قدیمی یا کالاهایی که واحد جدید دارند، بدون حذف اطلاعات انجام می‌شود.

مدیریت واحدها در تنظیمات به‌صورت یک پوشه/کارت بازشونده طراحی شده است تا صفحه اصلی تنظیمات خلوت بماند. حذف آخرین واحد مجاز نیست و واحدهایی که هنوز در کالاها استفاده می‌شوند در ذخیره‌سازی بعدی دوباره حفظ خواهند شد.

### ۱۴۰۵/۰۶/۲۹ — قرارداد تخصیص FIFO

تابع `settleChecksFIFO` فهرست فاکتورهای فروش معتبر را با `jalaliDateKey(invoice.date)` و فهرست چک‌های معتبر را با `jalaliDateKey(check.dueDate)` مرتب می‌کند. ترتیب ورود رکوردها و شماره‌ها در اولویت‌بندی مالی دخالت ندارند. برای هر چک، حلقه از قدیمی‌ترین فاکتور طرف حساب شروع می‌شود؛ تا وقتی اصل فاکتور کامل نشده، تخصیص به فاکتور بعدی انجام نمی‌شود. مقدار تخصیص‌یافته شامل اصل و سود روزشمار است و `principalAmount` برای سقف ۱۰۰٪ استفاده می‌شود.

`rebuildCheckAllocations` منبع واحد وضعیت فاکتورهاست و پس از عملیات چک، وضعیت، مبلغ پرداخت‌شده و ریز تخصیص همه فاکتورهای فروش را از ابتدا می‌سازد. بنابراین حذف یا تغییر وضعیت چک، فاکتورهای بعدی را نیز دوباره به ترتیب درست محاسبه می‌کند.

`jalaliDayDifference` با طول واقعی ماه‌های جلالی و اسفند کبیسه محاسبه می‌شود. `settings.dayBasis = "شمسی"` مخرج سود را بر اساس ماه تاریخ فاکتور تعیین می‌کند؛ مقدار عددی برای حالت‌های ثابت قدیمی باقی مانده است.

### ۱۴۰۵/۰۶/۲۹ — کنترل مغایرت آماری مشتری

کارت‌های فاکتورها باید فقط فروش معتبر را نمایش دهند؛ فاکتور باطل نباید در فروش ثبت‌شده یا ماندهٔ فروش وارد شود. بستن ماه فقط فاکتورهای فروش معتبرِ مشتری انتخاب‌شده را محاسبه می‌کند. برای جلوگیری از مقایسهٔ گمراه‌کننده، کنترل دامنهٔ بستن ماه سه مقدار را نشان می‌دهد: کل فروش معتبر، فروش مشتری انتخاب‌شده و فروش معتبر خارج از گزارش. اختلاف ۱۰۸ میلیون در سناریوی بازسازی‌شده برابر با ۸ میلیون فاکتور باطل و ۱۰۰ میلیون فاکتور خارج از شناسهٔ مشتری بود، نه خطای FIFO.

### ۱۴۰۵/۰۶/۲۹ — حذف فاکتور باطل و مرتب‌سازی

حذف فاکتور باطل در دفتر فاکتورها فعال است. چون موجودی هنگام باطل‌کردن قبلی اصلاح شده است، حذف فاکتور باطل نباید دوباره موجودی را تغییر دهد. برای فاکتورهای غیر باطل، منطق قبلی اصلاح موجودی حفظ شده است. کنترل مرتب‌سازی صعودی و نزولی برای فاکتورها، چک‌ها، اشخاص و کالاها اضافه شده است.

### ۱۴۰۵/۰۶/۲۹ — وضعیت انتشار حذف فاکتور باطل

نسخهٔ منتشرشده باید دکمهٔ واضح «حذف کامل فاکتور باطل» را در پنجرهٔ جزئیات فاکتور باطل نمایش دهد. این عملیات، فاکتور را از داده‌ها حذف می‌کند، موجودی را دوباره تغییر نمی‌دهد، تخصیص چک‌ها را بازسازی می‌کند و پنجرهٔ جزئیات را می‌بندد. اختلاف آمار ناشی از فاکتور باطل پس از حذف باید از هر دو گزارش فروش و مانده حذف شود.

### نسخه‌بندی و بازگشت پشتیبان‌ها

هر عملیات ساخت پشتیبان باید فایل مستقل تولید کند و هیچ نسخهٔ قبلی را overwrite نکند. قالب نام فایل `accounting-workshop-backup-YYYY-MM-DD-NNN.json` است؛ `YYYY-MM-DD` تاریخ شمسی و `NNN` شمارهٔ ردیف سه‌رقمی در همان روز است. در ذخیرهٔ محلی شمارنده در `localStorage` نگهداری می‌شود. در Google Drive شمارنده از فایل‌های موجود در پوشهٔ اختصاصی پروژه استخراج می‌شود. در نتیجه کاربر می‌تواند از فهرست Drive یا فایل‌های دانلودشده، نسخهٔ قدیمی‌تر را انتخاب و بازیابی کند. تاریخ ثابت نسخهٔ اولیه فقط به‌عنوان سابقهٔ قدیمی قابل مشاهده است و نباید به‌عنوان تاریخ امروز نمایش داده شود.

### وضعیت فعلی Google Drive و دسترسی مشتریان

کد فعلی مستقیماً از API مرورگر Google Drive استفاده می‌کند و تابع `getDriveAccessToken` فقط توکنی را می‌خواند که میزبان/اتصال OAuth در همان مرورگر در `window.__ACCOUNTING_DRIVE_ACCESS_TOKEN__` قرار داده باشد. GitHub Pages به‌تنهایی login یا refresh token امن ندارد؛ بنابراین نبود توکن باعث خطای ذخیره در Drive می‌شود و این خطا به معنی خراب‌بودن JSON یا پوشه نیست.

برنامهٔ فعلی برای یک مالک و دادهٔ محلی طراحی شده است. `partyId` فقط ارتباط حسابداری داخل یک مجموعه داده است و مجوز امنیتی ایجاد نمی‌کند. برای اینکه هر مشتری فقط اطلاعات خودش را ببیند، باید احراز هویت، جدول عضویت کاربر در tenant، فیلد `tenant_id` روی همهٔ مجموعه‌های مالی، سیاست‌های Row-Level Security، و API سمت‌سرور اضافه شود. فیلتر رابط به‌تنهایی راهکار امنیتی نیست.

### صفحه بانک‌ها و صندوق‌ها

صفحهٔ `banks` مرجع مدیریت حساب‌های `accounts` است. هر حساب دارای نام، نوع (`بانک`، `صندوق` یا `شریک`) و موجودی است. حساب‌های متصل به `checks.bankAccountId` قابل حذف نیستند تا ارجاع چک‌ها شکسته نشود. تغییر وضعیت چک به «وصول شده» موجودی حساب مقصد را از مسیر دفتر چک افزایش می‌دهد.

### تشخیص ذخیره‌نشدن Drive

وجود فایل قدیمی در پوشه فقط ثابت می‌کند که در یک زمان قبلی OAuth موفق بوده است. کد فعلی توکن را از `window.__ACCOUNTING_DRIVE_ACCESS_TOKEN__` می‌خواند؛ این توکن session-scoped و موقت است و GitHub Pages بدون OAuth Client و فرایند ورود نمی‌تواند آن را دوباره ایجاد کند. رفع واقعی یکی از این دو مسیر را لازم دارد: فعال‌سازی اتصال OAuth در میزبان/مرورگر یا افزودن Google Identity Services با OAuth Client ID و redirect مجاز. حدس‌زدن یا قراردادن credential در کد عمومی ناامن است.

### یکپارچگی مرجع چک و حساب

برای وضعیت‌های `نزد ما`، `وصول شده` و `برگشتی`، مقدار مرجع باید `checks.bankAccountId` باشد و به `accounts.id` با نوع بانک، صندوق یا شریک اشاره کند. فیلد متنی `checks.bank` فقط برای سازگاری با نسخه‌های قدیمی نگه داشته می‌شود. چک وصول‌شده با تغییر حساب، موجودی حساب قبلی را کم و حساب جدید را زیاد می‌کند؛ وضعیت برگشتی موجودی را زیاد نمی‌کند اما حساب امانت را نگه می‌دارد. حسابی که در چک استفاده شده باشد حذف‌پذیر نیست.

### Undo و Redo

تغییرات ذخیره‌شدهٔ همهٔ صفحات از مسیر مرکزی `commitState` عبور می‌کنند. برنامه حداکثر ۵۰ وضعیت قبلی و ۵۰ وضعیت قابل انجام دوباره را در حافظهٔ نشست نگه می‌دارد؛ این تاریخچه در backup ذخیره نمی‌شود و با refresh صفحه از نو شروع می‌شود. Undo و Redo دادهٔ کامل `AppState` را برمی‌گردانند، نه فقط یک فیلد. میانبرها خارج از ورودی‌ها فعال‌اند: `Ctrl/Cmd+Z` یک مرحله عقب، `Ctrl/Cmd+Y` یا `Ctrl/Cmd+Shift+Z` یک مرحله جلو. اگر پس از Undo تغییر جدید ثبت شود، مسیر Redo عمداً حذف می‌شود.

### مرجع حساب در چک

`checks.bankAccountId` اکنون می‌تواند به هر حساب `accounts` از نوع بانک، صندوق یا شریک اشاره کند. عنوان رابط از «بانک» به «حساب مرجع» تغییر کرده است. وضعیت وصول همچنان فقط برای حساب مرجع انتخاب‌شده موجودی را افزایش می‌دهد؛ نزد ما و برگشتی صرفاً مرجع نگهداری را ثبت می‌کنند.

### انتقال حساب و تسویه شریک

حساب `شریک` هم‌زمان می‌تواند برای نگهداری ماندهٔ تسویهٔ شریک استفاده شود. افزایش ماندهٔ آن در فرم «هزینه/خرید توسط شریک» به‌معنای افزایش طلب شریک از کارگاه یا بدهی کارگاه است؛ کاهش مانده در دریافت وجه توسط شریک، مساعده/پرداخت به شریک یا هر عملیات با اثر «کاهش طلب شریک» به‌عنوان تسویه یا کاهش تعهد ثبت می‌شود. کاربر باید حساب شریک، طرف حساب شریک، مبلغ، تاریخ و شرح را انتخاب کند.

انتقال بین حساب‌ها یک تراکنش با `fromAccountId` و `toAccountId` است. مبلغ از حساب مبدأ کسر و به حساب مقصد اضافه می‌شود؛ انتخاب مبدأ و مقصد یکسان مجاز نیست. در دفتر عملیات، شرح انتقال و اثر حسابداری نمایش داده می‌شود تا عملیات مالی قابل ردیابی باشد. تغییر موجودی و تراکنش هر دو از مسیر مرکزی ذخیره‌سازی و Undo/Redo عبور می‌کنند.

### مسیر اجرایی OAuth و پرتال مشتری

اتصال Drive اکنون در رابط پشتیبان یک مسیر OAuth رسمی دارد: Client ID عمومی Web در localStorage فقط برای راه‌اندازی جریان OAuth نگهداری می‌شود، اما access token فقط در حافظهٔ مرورگر می‌ماند. برنامه از Google Identity Services و scope محدود `drive.file` استفاده می‌کند. این scope برای شروع کم‌خطرتر است، اما فقط فایل‌هایی را پوشش می‌دهد که برنامه ایجاد یا کاربر از طریق برنامه مجاز کرده است؛ برای دسترسی به فایل قدیمی، کاربر باید همان فایل/پوشه را با برنامه مجاز کند یا از بازیابی دستی JSON استفاده کند. refresh token در GitHub Pages ذخیره نمی‌شود.

برای پرتال مشتری، معماری مورد تأیید این پروژه یک backend احراز هویت‌دار با جدول `tenants`، جدول `tenant_members`، حساب کاربری مشتری و جداول مالی دارای `tenant_id` است. همهٔ خواندن‌ها و نوشتن‌ها باید با سیاست‌های Row-Level Security کنترل شوند؛ فیلتر React، پارامتر URL، نام فایل Drive و Google Sheet عمومی مرز امنیتی نیستند. پورتال مشتری به‌صورت read-only فقط فاکتورهای همان مشتری، چک‌های تخصیص‌یافته به همان فاکتورها و گزارش بستن ماه او را نمایش می‌دهد. مدیر کارگاه امکان ثبت و اصلاح اطلاعات را دارد، اما مشتری فقط مشاهده می‌کند. اجرای این بخش نیازمند انتخاب و فعال‌سازی backend احراز هویت‌دار است و تا آن زمان دادهٔ مشتری نباید در لینک عمومی منتشر شود.

منابع رسمی: [Google Identity Services token model](https://developers.google.com/identity/oauth2/web/guides/use-token-model)، [Drive API authorization](https://developers.google.com/drive/api/guides/api-specific-auth)، [Supabase Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security).

### یکپارچگی عملیات مستقیم و فاکتورها

فاکتور مرجع رسمی خرید و فروش است و شامل طرف حساب، اقلام، قیمت، تخفیف، انبار و اثر کاردکس می‌شود. عملیات مالی مستقیم برای رویدادهایی است که فاکتور رسمی ندارند یا کاربر آگاهانه می‌خواهد یک رویداد انبار/نقدی مستقل ثبت کند. عملیات مستقیم خرید و فروش اکنون باید به کالا، انبار، طرف حساب، حساب مالی و مقدار متصل شود و در صورت پرداخت با چک، `checkId` نیز ذخیره می‌شود. خرید کالا موجودی را افزایش و حساب پرداخت را کاهش می‌دهد؛ فروش کالا موجودی را کاهش و حساب دریافت را افزایش می‌دهد. یک رویداد نباید هم در فاکتور و هم در عملیات مستقیم تکرار شود، چون باعث اختلاف فروش، موجودی یا مانده خواهد شد.

ویرایش و حذف عملیات مستقیم اثر حساب و موجودی را برمی‌گرداند و سپس اثر نسخهٔ جدید را اعمال می‌کند. بنابراین رکوردهای مستقیم، فاکتورهای رسمی و چک‌های تخصیصی سه منبع جدا اما دارای پیوند روشن هستند و گزارش‌ها نباید آن‌ها را بدون تشخیص نوع رکورد با هم جمع کنند.

### وضعیت Drive در موبایل

صفحهٔ پشتیبان در viewportهای باریک تک‌ستونه شده و کنترل‌های اتصال، فهرست و لینک‌ها به عرض صفحه محدود می‌شوند. هنگام اتصال OAuth پیام «در حال بازکردن پنجرهٔ مجوز» نمایش داده می‌شود. پس از دریافت توکن، فهرست Drive تازه‌سازی می‌شود. اگر پوشهٔ ثابت قدیمی با `drive.file` قابل مشاهده نباشد، برنامه فهرست و بارگذاری را در فضای فایل‌های ایجادشده توسط خود برنامه امتحان می‌کند و نتیجه را به‌صورت پیام واضح اعلام می‌نماید؛ این fallback جایگزین دسترسی به فایل‌های قدیمی نیست و برای آن بازیابی دستی JSON همچنان معتبر است.

### اعتبارنامهٔ Google Drive

شناسهٔ عمومی OAuth Web برای پروژهٔ `diesel-equator-450911-j4` در `client/src/lib/googleDrive.ts` ثبت شده است و به‌دلیل عمومی‌بودن Client ID، قرارگرفتن آن در bundle خطر افشای credential ندارد. Client Secret هرگز نباید در frontend، GitHub، backup، localStorage یا مستندات ذخیره شود. Client Secret ارسال‌شده در گفتگو باید افشاشده فرض شود؛ مالک پروژه باید از Google Cloud آن Client را حذف یا Secret را rotate کند و پس از آن فقط Client ID جدید/همان Client ID را در برنامه استفاده نماید. امنیت واقعی با Authorized JavaScript origins، OAuth consent screen، Test users و scope محدود `drive.file` کنترل می‌شود.

### پاک‌سازی OAuth در نشست‌های قدیمی موبایل

مرورگر گوشی ممکن است Client ID نسخهٔ قبلی را در localStorage نگه دارد. تابع `getDriveClientId` اکنون مقدار ذخیره‌شدهٔ متفاوت را نادیده می‌گیرد و Client ID عمومی معتبر پروژه را دوباره ثبت می‌کند. بنابراین پس از انتشار، کاربر باید صفحهٔ برنامه را با بازکردن مستقیم نشانی اصلی دوباره بارگذاری کند؛ در صورت نمایش bundle قدیمی، بستن تب و بازکردن دوبارهٔ صفحه یا پاک‌کردن cache سایت لازم است. پیام `invalid_client` به‌صورت جداگانه تشخیص داده می‌شود تا تفاوت آن با خطای Test User یا Origin روشن بماند.

### گزارش جریان نقدی

گزارش‌ها علاوه بر خلاصهٔ فروش، خرید، دریافت و پرداخت، دفتر جریان نقدی را از تراکنش‌های معتبر می‌سازند. برای جلوگیری از ابهام، دریافت، درآمد و فروش مستقیم به‌عنوان ورودی و پرداخت، هزینه، خرید مستقیم و سایر عملیات بدون علامت ورود به‌عنوان خروجی نمایش داده می‌شوند. برای هر ردیف، تاریخ شمسی، نوع عملیات، طرف حساب و حساب مرتبط نمایش داده می‌شود. انتقال بین حساب‌ها باید در تحلیل مدیریتی به‌عنوان انتقال داخلی در نظر گرفته شود و نباید به‌تنهایی درآمد یا هزینه تلقی شود.

کنترل تداخل، رکوردهای خرید/فروش مستقیم را با فاکتورهای معتبر از نظر نوع، تاریخ، طرف حساب، کالا و مبلغ مقایسه می‌کند. نتیجه یک هشدار احتمالی است، نه حذف خودکار؛ زیرا ممکن است عملیات مستقیم برای رویدادی بدون فاکتور ثبت شده باشد. اصل عملیاتی این است که یک رویداد اقتصادی فقط یک مرجع رسمی داشته باشد: فاکتور برای خرید/فروش رسمی و عملیات مستقیم برای رویدادهای مستقل.

### دفتر معین و تفصیلی

دفتر معین در صفحهٔ گزارش‌ها دو نمای مستقل دارد. نمای حساب، گردش بانک، صندوق و شریک را از عملیات مالی و وصول چک‌ها جمع می‌کند؛ انتقال بین حساب‌ها برای حساب مبدأ کاهش و برای حساب مقصد افزایش است. نمای طرف حساب، فاکتورهای معتبر، چک‌های دریافتی و تراکنش‌های دارای `partyId` را نشان می‌دهد. هر دفتر بر اساس تاریخ شمسی مرتب می‌شود و ماندهٔ تجمعی از افزایش منهای کاهش محاسبه می‌گردد.

این دفتر یک گزارش تحلیلی است و نباید به‌صورت جداگانه در موجودی حساب یا ماندهٔ طرف حساب ثبت شود؛ منبع اصلی داده همان فاکتور، چک و تراکنش است. فاکتورهای با وضعیت «باطل» و عملیات با وضعیت «باطل» وارد دفتر نمی‌شوند. برای خروجی کاغذی یا PDF از دکمهٔ چاپ مرورگر استفاده می‌شود.

### اصل تسویهٔ شریک با دو جهت مستقل

«حساب مالی شریک» محل گردش پول یا چک است؛ «طرف حساب شریک/ذی‌نفع» شخصی است که طلب یا بدهی او با کارگاه محاسبه می‌شود. این دو نباید یکی فرض شوند. عملیات `پرداخت بدهی کارگاه به شریک` باید از یک حساب کارگاه به حساب شریک ثبت شود و اثر آن کاهش طلب شریک از کارگاه باشد. عملیات `دریافت طلب کارگاه از شریک` باید از حساب شریک به حساب کارگاه ثبت شود و اثر آن کاهش طلب کارگاه از شریک باشد.

هر تسویهٔ شریک باید حساب مبدأ، حساب مقصد، طرف حساب، جهت، مبلغ، تاریخ و مرجع داشته باشد. مرجع می‌تواند فاکتور خریدی باشد که شریک شخصاً پرداخت کرده، چکی باشد که در حساب شریک وصول شده، هزینهٔ مستقل یا سایر رویدادهای مستند. حساب مبدأ و مقصد یکسان مجاز نیست. حساب مالی شریک برای اتصال و ردیابی انتخاب می‌شود، اما اثر ماندهٔ طلب/بدهی از `partnerEffect` و دفتر تفصیلی خوانده می‌شود تا مبلغ دوبار کسر نشود.

نمونهٔ خرید شخصی رسول: فاکتور خرید اسید استئاریک به طرف حساب رسول متصل می‌شود؛ کارگاه به رسول بدهکار می‌شود؛ هنگام تسویه، بانک کارگاه مبدأ و حساب شخصی رسول مقصد است و مرجع فاکتور ثبت می‌شود. نمونهٔ چک: چک مشتری در حساب رسول وصول شده؛ کارگاه از رسول طلبکار می‌شود؛ هنگام بازگشت وجه، حساب رسول مبدأ، بانک کارگاه مقصد و مرجع چک ثبت می‌شود.

### کاردکس یکپارچهٔ کالا

کاردکس هر کالا باید یک نمای زمانی از تمام رویدادهای مؤثر بر موجودی باشد. منابع آن عبارت‌اند از: اقلام فاکتور معتبر، عملیات مستقیم خرید/فروش معتبر و سوابق تولید. خرید و تولید «ورود» و فروش و مصرف ماده در تولید «خروج» هستند. هر رویداد باید مرجع، تاریخ، مقدار، واحد، انبار و ارزش داشته باشد. در دادهٔ فعلی، انبار فاکتور از محل نگهداری کالا و انبار عملیات از `warehouseId` خوانده می‌شود؛ ثبت تولید نیز از انبار محصول و انبار مواد فرمول استفاده می‌کند.

فاکتور یا عملیات باطل نباید در کاردکس نمایش داده شود. کاردکس مانده را دوباره روی `products.stock` اعمال نمی‌کند، چون موجودی اصلی هنگام ثبت/ویرایش/حذف سند اصلاح می‌شود. بنابراین این صفحه برای کنترل و ردیابی است و از دوباره‌شماری موجودی جلوگیری می‌کند. اگر کاردکس با موجودی فعلی اختلاف داشت، ابتدا سند باطل، اصلاح دستی، ویرایش فاکتور، عملیات مستقیم و تولید بررسی می‌شوند.

### گزارش سود و مطالبات

گزارش سود فعلی باید بین «سود ناخالص تقریبی مدیریتی» و «سود قطعی حسابداری» تفاوت بگذارد. سود تقریبی از فروش فاکتورهای معتبر منهای مقدار پایهٔ اقلام فروش ضربدر قیمت پایهٔ فعلی کالا به‌دست می‌آید؛ چون قیمت پایه ممکن است بعداً تغییر کند، این شاخص برای دید سریع مناسب است و نباید به‌عنوان بهای FIFO قطعی ثبت شود. فاکتورهای باطل در فروش و خرید معتبر نیستند.

ماندهٔ طرف حساب در داشبورد از فروش معتبر منهای خرید معتبر و مبلغ `paidAmount` محاسبه می‌شود. برای تحلیل دقیق‌تر مشتری، بستن ماه و تخصیص چک همچنان مرجع اصلی تسویه است؛ داشبورد سود و مطالبات یک خلاصهٔ مدیریتی است و نباید جایگزین FIFO، سود دیرکرد یا دفتر تفصیلی شود. مبالغ با ماندهٔ مثبت به‌عنوان بدهکار و ماندهٔ منفی به‌عنوان بستانکار نمایش داده می‌شوند.

### گزارش سنی مطالبات و بدهی‌ها (Aging)

گزارش Aging ابزار اولویت‌بندی پیگیری وصول و پرداخت است، نه جایگزین تخصیص FIFO. سن هر فاکتور از تاریخ فاکتور تا تاریخ شمسی روز محاسبه می‌شود. فاکتور فروش باز، طلب کارگاه از مشتری است؛ فاکتور خرید باز، بدهی کارگاه به فروشنده است. مبلغ باز برابر `max(0, amount - paidAmount)` است. گروه‌های فعلی ۰–۳۰، ۳۱–۶۰، ۶۱–۹۰ و بیشتر از ۹۰ روز هستند. فاکتورهای باطل در گزارش وارد نمی‌شوند.

برای گزارش دقیق سررسید چک، وضعیت چک، تخصیص FIFO و بستن ماه همچنان باید بررسی شود؛ Aging فقط سن سند و ماندهٔ ثبت‌شده را خلاصه می‌کند.

### صورت‌حساب تفصیلی مشتری

صورت‌حساب مشتری یک گزارش خواندنی و قابل چاپ است و برای هر مشتری از فاکتورهای معتبر و چک‌های مرتبط ساخته می‌شود. فروش بدهکار و خرید بستانکار مشتری است. چک دریافتی بستانکار مشتری محسوب می‌شود و چک برگشتی یا عودت‌شده بدهکار می‌شود تا اثر آن بر مانده برگشت کند. ماندهٔ هر ردیف به‌صورت تجمعی از بدهکار منهای بستانکار محاسبه می‌شود.

این گزارش جایگزین احراز هویت مشتری یا پرتال آنلاین امن نیست. خروجی CSV و چاپ برای استفادهٔ مالک یا حسابدار داخلی است؛ دسترسی مستقل مشتری به اطلاعات خود نیازمند احراز هویت سمت‌سرور و Row Level Security است و در مرحلهٔ معماری پرتال پیاده‌سازی خواهد شد.

## وضعیت انتشار پیش از APK

نسخهٔ فعلی برای استفادهٔ واقعی در مرورگر و نصب به‌عنوان PWA آماده است، اما هنوز نسخهٔ نهایی APK نیست. مسیرهای نصب و service worker برای GitHub Pages نسبی شده‌اند و آیکون‌های نصب اضافه شده‌اند. پیش از APK باید دورهٔ آزمون واقعی طبق `docs/PRE-APK-TEST-GUIDE.md` انجام شود؛ به‌ویژه FIFO، بستن ماه، تولید، موجودی، پشتیبان/بازیابی و کارکرد موبایل باید با دادهٔ واقعی تأیید شوند.

تبدیل PWA به APK محدودیت local-first و نبود احراز هویت سمت‌سرور را برطرف نمی‌کند. پرتال امن مشتریان و دسترسی جداگانهٔ هر مشتری نیازمند backend، احراز هویت و Row Level Security است.

## قواعد جدید تبدیل واحد و تولید

موجودی داخلی هر کالا در واحد اول ذخیره می‌شود. مقدار ورودی با تابع تبدیل عمومی به واحد اول تبدیل می‌شود. اگر واحد اول و واحد انتخابی از خانواده‌های استاندارد جرم، حجم یا طول باشند، نسبت واقعی استاندارد اعمال می‌شود؛ برای واحدهای بسته‌ای مانند کارتن، نسبت تبدیل اختصاصی کالا ملاک است. بنابراین واحد اول «کیلوگرم» و مقدار «۳۶۰ گرم» به‌صورت ۰٫۳۶ در موجودی ذخیره می‌شود، نه ۳۶۰ کیلوگرم.

موجودی اولیه واحد ورودی جداگانه دارد و پیش‌فرض آن واحد دوم کالا است، ولی کاربر می‌تواند واحد اول را دستی انتخاب کند. مقدار پایه و قیمت پایه باید همیشه بر اساس واحد اول محاسبه شوند. مقادیر اعشاری در همهٔ فرم‌های مقدار با `inputMode="decimal"` پذیرفته می‌شوند.

فرمول بستهٔ تولید مستقل از قطعه است. هنگام تولید، اگر خروجی بسته محصولی از قبل نداشته باشد، یک کالا با دستهٔ «بسته تولید» در انبار مواد اولیه ساخته می‌شود. این کالا در فرمول‌های بعدی به‌عنوان مادهٔ اولیه قابل انتخاب است. فرمول قطعه مستقیماً به محصول خروجی لینک می‌شود. بهای جاری فرمول از قیمت فعلی مواد و سربار ذخیره‌شده محاسبه می‌شود؛ سابقهٔ تولید قبلی برای حسابرسی باقی می‌ماند.
